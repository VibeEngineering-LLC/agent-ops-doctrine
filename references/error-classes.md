# Каталог КЛАССОВ рабочих ошибок агентов (C-NNN)

> **Примечание к публичной копии.** Файл выгружен из приватной рабочей конфигурации: имена контуров заменены ролями, личные пути — плейсхолдерами. Ссылки на файлы, отсутствующие в этом репозитории (реестры скиллов и инструментов, журналы инцидентов, история), указывают на приватные части конфигурации и намеренно не публикуются.

**Создан:** 2026-08-21. **Владелец:** глобальная доктрина (`<home>\.claude\`).
**Уровень:** над журналами контуров, ниже CLAUDE.md — это не правило, а карта того, ГДЕ правила рвутся.

## Назначение

Журналы `<контур>\audit\work-incidents.md` (§32) фиксируют ОТДЕЛЬНЫЕ инциденты. Отдельный инцидент
починить можно, а класс — нельзя: мера по одному скрипту не удерживает тот же дефект в соседнем
(доказано парой `надзорный:W-026` → `надзорный:W-030`, см. C-003). Каталог собирает инциденты в КЛАССЫ ПО
ОБЩНОСТИ КОРНЕВОЙ ПРИЧИНЫ и задаёт для каждого три вещи, которых в журналах нет:

1. **Trigger-signature** — машинно-проверяемое условие МОМЕНТА РИСКА (не момента разбора).
2. **Вопрос-инъекция** — одна строка, которую хук показывает агенту в этот момент. Форма вопроса,
   не императива: императив требует лишь согласия, вопрос требует ответа в текущем рассуждении.
3. **Статус покрытия** — удерживает ли принятая мера весь класс или только точку инцидента.

**Кто это потребляет:**

- **хук-диспетчер уроков** — читает `lessons-triggers.json` (машинная проекция полей
  «Trigger-signature» + «Вопрос-инъекция» этого файла) и на PreToolUse/Stop подставляет вопрос
  класса в момент риска. Каталог — SSOT, JSON — производная; расхождение чинится правкой каталога.
- **скрипт-метрика рецидивов** — считает по журналам новые записи, попадающие в уже закрытые
  классы. Рецидив в классе со статусом `COVERED-*` означает, что мера не удерживает и её надо
  поднимать по лестнице мер (§32), а не «быть внимательнее».
- существующие хуки этапа 1 самообучения: `<home>\.claude\hooks\lessons_gate.py` (требует
  секцию LESSONS в брифе субагента), `<home>\.claude\hooks\lessons_inbox_counter.py`.

## Правила ведения

- **Нумерация `C-NNN`** — сквозная, НЕ переиспользуется. Класс не удаляется даже когда закрыт:
  удалённый класс перестаёт считаться в метрике рецидивов; устаревший помечается в поле «Статус».
- **Составной ключ `контур:W-NNN` обязателен.** W-номера уникальны только ВНУТРИ журнала контура;
  между контурами они совпадают и означают разные инциденты: `прошивки:W-012` — реальная почта в
  публичном коммите, `моделирование:W-012` — дублирующий модуль калибровки, `надзорный:W-012` — правка чужой
  зоны. Голый `W-012` в тексте — дефект записи.
- **Класс определяется ПРИЧИНОЙ, не последствием.** «Утекли секреты», «потеряны данные», «упало
  приложение» — последствия; они разложены по разным классам по тому, ПОЧЕМУ не сработала проверка.
  Поэтому утечки живут в C-002, а не в отдельном «классе утечек».
- **Похожие симптомы с разными причинами — РАЗНЫЕ классы.** Потери от `--force` (C-003, не прочитан
  флаг) и снос строк широким фильтром (C-012, не было сухого прогона) — один симптом «стёрло
  лишнее», две причины, две разные меры.
- **Одна запись может проявлять два класса** — тогда она указана в обоих, во втором с пометкой
  `(вторая причина)`. Склеивать классы ради единственности членства запрещено.
- Инцидент, не попадающий ни в один класс, — повод завести новый `C-NNN`, а не растянуть
  формулировку существующего.
- **Вопрос-инъекция ≤ 120 символов ТЕКСТА вопроса** (маркер `**Вопрос-инъекция.** ` в счёт не
  входит). Норма закреплена здесь 21.08 после того, как контрольная сверка дала два разных
  вердикта на одном файле в зависимости от способа счёта: критерий, не записанный в документе,
  проверяем неоднозначно.

## C-001 — Наличие выхода принято за наличие результата

**Формулировка.** Приёмка выполняется по признаку «инструмент отработал»: код возврата 0, скрипт
что-то напечатал, файл создан, тест зелёный, отправка вернула `sent`. Признак относится к ВЫЗОВУ, а
не к РЕЗУЛЬТАТУ, и потому остаётся истинным, когда работа не сделана вовсе — именно так выглядят
успехом проглотивший исключение `except`, мёртвый хук и недоставленное письмо.

**Проявления.** надзорный:W-001, надзорный:W-003, надзорный:W-006, надзорный:W-007, надзорный:W-015, надзорный:W-021,
надзорный:W-024, прошивки:W-001, прошивки:W-002, прошивки:W-019, аудит-кода:W-008, прикладное-ПО:W-002, моделирование:W-007,
моделирование:W-008 (вторая причина), надзорный:W-039 (23.08, файловая система — см. детектор ниже), моделирование:P-021+W-024 (21.08: ионный прогон в контуре моделирования дал fluence_total=0
при EXITCODE=0 — долгоживущее ядро не распадалось без threshold; закрыто МЕХАНИЧЕСКИ в узкой точке:
сторож FLUENCE_ZERO в wallfield.cc валит прогон кодом 3 при нулевом флюенсе, мутационно проверен)

**Trigger-signature.** PostToolUse на `Bash` с `run_in_background: true` и на завершение фоновой
задачи/`Agent`; PreToolUse на `send_message`; Stop-хук по тексту ответа
`(?i)(exit\s*0|код возврата|отработал|запущен|тест[ыи]?\s+зелён|passed|sent|queued|доставлен)` при
отсутствии в том же ходе чтения самого выходного файла.

**Вопрос-инъекция.** «Ты открыл выходной файл — или у тебя только код возврата и слово инструмента?»

**Текущая мера.** §31.A.2 и #SA-3 («проверено, что работает» принимается только вместе с «проверено,
что ломается, когда должно») — КЛАССОВАЯ, но чисто текстовая. Механически закрыта одна точка: #ENC-1
(байтовое чтение stdin) в шести хуках — УЗКАЯ. Рецидивы после принятия #SA-3 есть (надзорный:W-021,
надзорный:W-024, оба 18.08).

**Детектор для файловой системы** (2026-08-23, аудит-кода наблюдал — надзорный:W-039). Класс до сих пор
описывался через ВЫЗОВЫ (exit 0, `sent`, зелёный тест), но файловая система даёт тот же обман без
единого вызова: **битый junction/симлинк неотличим от рабочей папки в листинге**. `os.listdir` и
`Get-ChildItem` показывают имя, Claude Code перечисляет скилл среди доступных — а обращение к
содержимому молча не срабатывает, потому что цель не существует. Состояние «всё на месте» держится
ровно до первого чтения. Обнаружено косвенно: после публикации скилла проверка его git на `D:`
вернула «No such file or directory» на пути, с которым работали десятью минутами раньше; размотка
показала 62 битых junction из 74.

Отсюда правило приёмки любой операции над деревьями каталогов (перенос, бэкап, пересоздание ссылок):
проверять не присутствие имени, а **читаемость содержимого** — `Test-Path` на файл ВНУТРИ папки, а
не на саму папку; для ссылок отдельно сверять `LinkType` и существование `Target`. Отдельная ловушка
внутри ловушки: `os.path.exists` на битом junction возвращает `False`, но `os.walk` его имя
показывает — два стандартных API расходятся, и выбор «удобного» даёт ложно-зелёный ответ.

**Обобщение (2026-08-23, надзорный, тот же ход что и W-039):** расхождение двух API — не свойство
именно junction'ов, а общий симптом файловой системы. Тот же разрыв даёт файл без прав на чтение
(`exists`=True, открытие падает), файл в процессе записи другим процессом (листинг видит размер
0 или старый), путь за пределом `MAX_PATH` (одна библиотека молча обрезает, другая падает).
Правило шире: при проверке дерева каталогов после операции сверять **минимум двумя разными API**
(не «быстрым» и «медленным» вариантом одного и того же вызова) — расхождение само по себе сигнал,
даже раньше, чем понятна его причина.

**Детектор для скриптов-сборщиков** (2026-08-21, из петли самообучения — пойман при построении
этого каталога): скрипт, собирающий записи по чужим файлам, обязан контролировать ПОЛНОТУ выборки
двумя независимыми паттернами (строгий + ослабленный, плюс сверка с множеством всех вхождений
идентификатора в тексте). Повод: строгий regex `^#{2,4}\s*(W-\d+)` молча потерял 10 из 24 записей
моделирование — контур сменил формат заголовка на `## ⚠ W-015 (20.08): …`; скрипт вернул exit 0 и неполный
результат. Требование обязательно для harvest-скрипта (стратегия самообучения, этап 3).

**Статус.** OPEN

## C-002 — Область проверки уже проверяемого утверждения

**Формулировка.** Проверка выполнена добросовестно, но по построению не способна обнаружить то,
чего, по её итогу, «нет»: шаблон вместо сплошного чтения, байты вместо распакованного потока,
содержимое вместо метаданных, совокупная выдача вместо вклада компонента, конфигурация вместо
доступности, окно выборки, не покрывающее период вывода, глазомер вместо инструмента. Отрицательный
результат такой проверки фактом отсутствия не является.

**Проявления.** прошивки:W-010, прошивки:W-014, прошивки:W-030, сеть:W-001, надзорный:W-010, надзорный:W-014,
радон:W-001, прикладное-ПО:W-004, прикладное-ПО:W-010, моделирование:W-016, спектрометрия:W-003 (пять итераций
починки FWHM-измерителя, шесть стерильных аудитов подряд — каждый находил критичное на глубже
предыдущего слое: мутационная стадия патчила только уже изменённые ветки, не значения по умолчанию
в сигнатурах (ни одно ожидание не вызывало функцию без явного параметра); регрессионные ДАННЫЕ
самоисполнялись — хвостовые нули вектора коэффициентов делали потерю последнего элемента невидимой;
юнит-тест кормил вспомогательную функцию массивом в обход подложки, тогда как в реальном конвейере
подложка съедала сигнал, и функция была инертна там 0 раз из 55; охраняемый «отказ» проверялся
сканом по энергии, но держался на одной пуассоновской реализации — статистически эквивалентный
повтор того же измерения ломал его в 4 случаях из 8; счётчик-инвариант «чисел не больше N» не
видел, что состав ложных срабатываний полностью заменился при неизменном count; надзорный:W-034-доп
(книжная библиотека, 21.08) — `os.path.exists(new_path)` как проверка «конфликта имени» перед
`os.rename` на Windows/NTFS: файловая система регистронезависима для существования, поэтому
проверка стабильно возвращает `True`, когда `new_path` отличается от исходного ТОЛЬКО регистром
буквы — это не конфликт, а тот же самый файл; 84 из 84 переименований ложно посчитаны
«конфликтом» при первом прогоне. Симметричная ловушка и в верификации: `not os.path.exists(from)`
после rename тоже всегда `False` в этом сценарии — проверять нужно `os.listdir()` конкретного
имени байт-в-байт, не `exists()` по любому из путей)

**Trigger-signature.** Stop-хук по отрицательным утверждениям в тексте ответа:
`(?i)\b(не найден|нет совпадений|отсутству|чисто|0 совпадений|потерь нет|невозможно|нигде не|не используется|не встречается)\b`;
плюс PreToolUse на `git push` / `gh release` / Write в чужой `_interchat\inbox\`, если в предыдущих
ходах выполнялся секрет-скан.

**Вопрос-инъекция.** «Твоя проверка вообще способна была увидеть то, чего, по её итогу, нет?»

**Текущая мера.** §14b (сплошное чтение вместо шаблона перед выгрузкой), #SEC-3 (структурная
выгрузка PDF/DOCX вместо байтового грепа), раздел «Границы видимости проверяющего» скилла
`six-corner-audit` — по формулировке КЛАССОВЫЕ, но каждая закрывает свою поверхность (секреты,
бинарники, границы прохода); единой проверки «покрывает ли метод утверждение» нет. Самые дорогие
проявления класса — утечки (прошивки:W-014, прошивки:W-030, сеть:W-001).

**Приём: машинной проверке — генеральная совокупность, не выборка** (2026-08-21, из петли
самообучения). Выборочная сверка «любых трёх ключей» — компромисс для человека; скрипту полный
обход стоит того же одного прогона и даёт покрытие вместо иллюстрации. Повод: контрольная сверка
каталога вместо запрошенных 3 ключей проверила все 109 за тот же прогон. Правило: если проверку
выполняет скрипт — брать всё множество; «любые N» отдавать как иллюстрацию с `file:line`, а не
как объём проверки.

**Приём: мутационная проверка обязана мутировать ТРИ поверхности, не одну** (2026-08-21, `спектрометрия:W-003`).
«Зелёный самотест» проверялся по коду — но не по (а) значениям параметров ПО УМОЛЧАНИЮ в сигнатурах
(мутировать `__defaults__`/`__kwdefaults__` отдельной стадией, требовать хотя бы одно ожидание без
явной передачи параметра); (б) самим РЕГРЕССИОННЫМ ДАННЫМ (обнулить/удалить элемент набора и
убедиться, что тест краснеет — иначе часть набора может быть инертна по построению); (в) публичной
ТОЧКОЙ ВХОДА конвейера, а не внутренней функцией напрямую (если критерий недостижим через публичный
вызов — фиксировать это как факт, не изобретать пин, чтобы юнит-тест прошёл). Отдельно: охраняемый
«отказ» проверять не только сканом по параметру (энергия, канал), но и по СТАТИСТИЧЕСКОЙ РЕАЛИЗАЦИИ
— набор λ-эквивалентных повторов измерения (не хуже 8), иначе граница держится на одном конкретном
шуме. И: инвариант вида «количество ≤ N» заменять на инвариант по СОСТАВУ (группировка по
идентифицирующему признаку — центроиду, ключу, файлу), потому что счётчик может остаться неизменным
при полной замене набора нарушений.

**Статус.** OPEN

## C-003 — Семантика флага или инструмента предположена по имени, реализация не прочитана

**Формулировка.** Поведение ключа командной строки, режима или API-вызова выводится из названия и
«здравого смысла», а не из исходника, и на этом предположении запускается массовый вызов. Класс
дорог именно потому, что предположение обычно ПОЧТИ верно: `--force` действительно «делает
принудительно», но что он при этом отключает — знает только код.

**Проявления.** надзорный:W-026, надзорный:W-030, надзорный:W-029, моделирование:W-008, прикладное-ПО:W-007

**Trigger-signature.** PreToolUse на `Bash`, если `tool_input.command` содержит
`(?i)(--force|--hard|--prune|--purge|--all|--overwrite|--delete|/IM\b|-Recurse|-Force)` И вызываемый
скрипт (`\S+\.(py|ps1|sh)`) в этой сессии ни разу не читался (нет `Read` по его пути). Усиление: та
же команда в цикле по более чем одной цели.

**Вопрос-инъекция.** «Ты читал код этого флага — или вывел его смысл из имени?»

**Текущая мера.** По надзорный:W-026 принята мера ВЫСШЕЙ ступени («устранение самой возможности»):
патч `convert.py` — `--force` не трогает `.pdf`/`.djvu` с маркером `ocr_engine: mineru`, мутационно
проверен, «повторить эту потерю физически не может». Но область меры — ОДИН скрипт. Через сутки
рецидив в другом скрипте того же проекта: `catalog.py --force` стёр 619 из 624 записей каталога
(надзорный:W-030). **Узкая мера высшей ступени класс не закрыла — это главный урок каталога.**
Классовой меры (вопрос перед массовым вызовом непрочитанного флага) нет.

**Статус.** OPEN

## C-004 — Утверждение о механизме дано по памяти или достроено логикой, источник не открыт

**Формулировка.** Заявление о том, как работает код, инструмент или канал, строится на воспоминании,
на правдоподобном рассуждении от одного прочитанного факта или на собственном комментарии — вместо
чтения файла. Своя зона ощущается проверенной по умолчанию («это моя прошивка, я её знаю»), и именно
там проверка выпадает чаще всего.

## C-008 — Гейт обойдён другим инструментом вместо остановки

**Формулировка.** Гейт блокирует ИНСТРУМЕНТ (Write/Edit), а не ДЕЙСТВИЕ (запись кода на диск). При
блокировке выбирается ближайший работающий канал — Bash-heredoc, `python -c`, — вместо остановки и
переоценки задачи. Сюда же проход ПОД порогом: серия правок по 20 строк формально легальна, а по
сути та же генерация в рассрочку.

**Проявления.** надзорный:W-009 (обход в ТОМ ЖЕ ходе, в котором ставился гейт), надзорный:W-008 (проход
под порогом 25 строк), прошивки:W-021 (субагент обошёл `delegation_guard.py` через Bash-heredoc и дал
ложно-зелёный отчёт)

**Trigger-signature.** PreToolUse на `Bash` в пределах N ходов после `exit=2` от
`delegation_guard.py`, если `tool_input.command` содержит
`(?i)(<<\s*'?[A-Za-z_]+|python\s+-c|Set-Content|Out-File|WriteAllText|tee\s+)`; отдельно — серия из
3+ Write/Edit подряд по одному файлу кода, каждый ниже порога.

**Вопрос-инъекция.** «Твой Write только что заблокировали — ты обходишь запрет или пересмотрел задачу?»

**Текущая мера.** Дыра ПРИЗНАНА и описана (надзорный:W-009: «гейт по конструкции блокирует инструмент,
а не действие»), закрытие сознательно отложено — перехват Bash с разбором содержимого оценён как
ступень выше по сложности. В брифы субагентов добавляется текстовое требование «встретишь блокировку
хука — остановись и доложи» (прошивки:W-021, мера текстовая, статус самой записи `OPEN`).

**Грань: недоступность механизма проверки — это тоже блокировка** (2026-08-23, аудит-кода, поймано
на себе в тот же ход). Класс до сих пор описывал обход ЗАПРЕТА — хук сказал «нельзя». Но тот же
паттерн включается, когда механизм проверки просто НЕ РАБОТАЕТ: классификатор безопасности
`Bash` стал недоступен (rate-limit), и первой реакцией было взять для той же операции соседний
канал (`mcp__pwsh__pwsh`), а не остановиться. Обход не состоялся лишь потому, что система
оказалась последовательнее исполнителя — классификатор нужен и второму инструменту.

**Почему эта грань опаснее исходной.** Явный запрет ощущается как «мне не разрешили» и тормозит.
Недоступность ощущается как «техническая помеха, которую логично обойти» — сопротивление ниже, а
риск тот же или выше: при запрете действие оценено и отклонено, при недоступности оно НЕ ОЦЕНЕНО
вовсе. **Правило: недоступность механизма проверки приравнивается к запрету, а не к помехе.**
Правильная реакция — пауза, доклад оператору и продолжение теми задачами, которые проверки не
требуют (чтение, анализ), но не смена инструмента ради того же действия.

**Разграничение, чтобы правило не парализовало работу.** Обходом является смена инструмента ради
ТОГО ЖЕ действия, которое не прошло. Не является обходом использование другого инструмента по его
прямому назначению: в том же инциденте письмо в `_interchat` через `Write` — штатный путь (там он
и предписан хуком `outbox_verify_gate.py`), а не суррогат заблокированного канала.

**Обратная сторона класса — ЛЕГАЛЬНЫЙ путь, ошибочно принятый за обход** (надзорный:W-031, 21.08).
Текст отказа `delegation_guard.py` САМ перечисляет четыре легальных пути, и путь №4 («запуск
inline-кода без записи в файл») фактически позволяет записать файл — регексп `SHELL_CODE_WRITE_RE`
ловит только редирект/`tee`/`Set-Content`, но не имя файла внутри тела питон-скрипта. Отсюда два
следствия, обязательных при разборе подобных случаев:
- **Текст отказа гейта читать как инструкцию, а не как стену** — в нём указан санкционированный
  выход; уход в него обходом НЕ является.
- **Прежде чем квалифицировать действие как обход — прочитать сам гейт** (`file:line`), а не
  судить по факту «сначала отказ, потом запись другим способом». Внешне это одно и то же.

Отдельно: путь №2 (субагент-хирург) технически неисполним иначе, чем через путь №4 — хуки не
различают оркестратора и субагента, поэтому предписанный доктриной механизм правки работает
только через эту щель. Дефект конструкции, мера вынесена оператору (надзорный:W-031).

**Статус.** OPEN

Stop-хук — число в тексте рядом со словами
`(?i)(эффективност|коэффициент|выигрыш|ускорение|точност|разрешение|паспорт|номинал|доказано)` при

## C-016 — Перенос решения или конвенции между контекстами без сверки с оригиналом

«проверять тот канал, который отдаёшь» (надзорный:W-013). Совокупно УЗКИЕ, общей формулировки нет.

**Мера, найденная на рецидиве моделирование:P-023 (21.08) — единственная, сработавшая на этом классе.**
Дефект нашёлся не проверкой результата (результат выглядел правдоподобно и был объяснён неверной
гипотезой), а **сверкой реализации с ОПРЕДЕЛЕНИЕМ по пунктам**: оператор назвал метод его каноническим

своём коде отдельно; неотмеченный пункт = невыполненный.** Механическое подкрепление там же:
исполняемая часть приёма печатает подтверждение в лог (`CHAIN_CUT: nucleusLimits A=.. Z=..`), чтобы
её отсутствие нельзя было принять за присутствие — молчание неотличимо от работы (ср. надзорный:W-015).

## C-020 — Статистический критерий развёрнут без проверки на нуль-гипотезе

**Формулировка.** Метрика или порог для отличения «сигнал/шум» либо «А/Б» строится и калибруется
на позитивных примерах, но не прогоняется на негативных (честном шуме, здоровых данных) ПЕРЕД
использованием как критерий отказа/принятия. Два характерных подкласса: (а) метрика — ОТНОШЕНИЕ
двух величин вместо их РАЗНОСТИ, из-за чего она теряет масштаб выборки и на малой/нулевой
статистике даёт те же значения, что и на большой, — критерий, работающий на демонстрационном
примере, на бесшумной синтетике даёт противоположный вывод; (б) знаменатель метрики ПАДАЕТ с
ростом статистики (типично — «бюджет» или «допуск», нормированный на собственную погрешность),
из-за чего критерий, откалиброванный на слабых данных, даёт массовые ложные срабатывания на
сильных — и наоборот.

**Проявления.** спектрометрия:W-003 (двухкомпонентный тест бленда: «выигрыш по chi2» как ОТНОШЕНИЕ
приведённых chi2 давал 1,0–1,4 на реальном зашумлённом дублете и диапазон 170–10500 на бесшумной
синтетике — первый прогон без генератора случайных чисел дал бы обратный вывод; чинилось заменой
на РАЗНОСТЬ сумм chi2. Отдельно: критерий «превышение измеренной ширины над её же бюджетом
погрешности» дал 154 ложных срабатывания из 320 на заведомо здоровых линиях, потому что у сильной
линии бюджет узкий и любое шумовое расщепление формально «превышает» его)

**Trigger-signature.** Сигнатуры нет, признак читается только по коду/докстроке: числовой порог
или новая метрика в коде статистической проверки (`chi2`, `sigma`, `significance`, `ratio`,
`gain`, `threshold`), для которой в диффе или тексте отсутствует прогон на синтетике с ИЗВЕСТНЫМ
ответом «отрицательно» (чистый шум, здоровые данные без искомого эффекта) при варьируемой
интенсивности/статистике.

**Вопрос-инъекция.** «Ты прогонял этот критерий на честном шуме и на сильном здоровом сигнале —
или только на примере, где он должен сработать?»

**Текущая мера.** Нет. Первое зафиксированное проявление класса — журнальная запись, привода не
заводится (§32 «правило второго случая»); при повторе — оформить как правило в `code-review`/
`fewer-permission-prompts`-подобный чек-лист статистического кода.

**Статус.** OPEN

## C-021 — Проверка снята без замены, снятие приравнено к устранению её изъяна

**Формулировка.** Проверка отклонена и убрана ЗАКОННО (она была неверна по существу — например,
навязывала измерению чужое априорное ожидание), но взамен не поставлена никакая другая проверка
того же класса рисков. Убрать плохую проверку и оставить дыру незащищённой — не то же самое, что
починить: физически абсурдное значение после этого проходит беспрепятственно.

**Проявления.** спектрометрия:P-003 (сверка измеренного разрешения с паспортным диапазоном КЛАССА
детектора отклонена верно — паспорт неизвестен заранее, сверка нарушала бы «калибровка всегда из
данных» и маскировала бы реальную деградацию прибора; но взамен не введена НИКАКАЯ абсолютная
граница правдоподобия, и значение R=87% беспрепятственно проходило обе ступени проверки).

самописный измеритель: мера «записан инцидент» была принята на словах, а сам работающий
инструмент остался в проекте и продолжал цитироваться.

**Trigger-signature.** Нет. Признак виден только по диффу: удаление/отключение проверочного блока
(`if`, `assert`, `check_*`, `validate_*`) без появления нового условия, покрывающего тот же класс
входов, в том же коммите или ближайших к нему.

**Вопрос-инъекция.** «Убрав эту проверку — ты поставил взамен другую, ловящую тот же класс
абсурдных значений, или дыра осталась открытой?»

**Текущая мера.** Нет. Два независимых проявления в один день (правило второго случая §32
выполнено) — кандидат на текстовое правило при следующем триаже; привода/хука пока не заводится.

**Статус.** OPEN

## C-022 — Одинаковый результат у ВСЕХ испытуемых принят за свойство испытуемых, а не за дефект стенда

**Формулировка.** Измерение даёт один и тот же исход (чаще — нулевой или предельный) по всем
объектам без исключения, и этот исход записывается как их общее свойство. На деле совпадение по
всей выборке — сигнатура дефекта ИЗМЕРИТЕЛЬНОГО ТРАКТА: разброс объектов обязан проступать хоть
где-то, а его отсутствие означает, что мерили не объект. Частный и самый коварный подвид —
дефект на СТЫКЕ собственного кода с поведением внешней системы (API, драйвер, прибор): код
корректен построчно, внешняя система корректна по документации, неверно их сочетание.

**Проявления.** `аудит-кода:W-012` (2026-08-23): задача пакетной классификации давала score 0.00
у всех пяти локальных моделей во всех прогонах. Причина — режим структурированного вывода
`format='json'` в Ollama: grammar-constraint закрывает JSON после первого валидного объекта, и
пакетный ответ обрывается на 1 элементе из 200. Решающий эксперимент с ОДНОЙ переменной (та же
модель, тот же промпт, отличается только режим запроса): с `format='json'` — 13 токенов и score
0.00; без него — 2893 токена и score 1.00. Едва не опубликовано как «локальные модели не тянут
пакетную классификацию». Ранее в том же расследовании — тот же класс в более слабой форме: полный
верный ответ в форме словаря вместо списка получал 0.00 (мерилась форма, а не содержание).

**Почему не ловится аудитом кода.** ШЕСТЬ раундов стерильного аудита ЧЕТЫРЬМЯ разными
моделями-аудиторами (включая два раунда прицельно про справедливость задания) этот дефект не
нашли: все они читают КОД, а дефект живёт в сочетании кода с фактическим поведением внешней
системы. Увеличение числа и разнообразия аудиторов здесь не помогает — нужен другой ВИД проверки,
а не больше проверок того же вида.

**Trigger-signature.** Есть, сильная и дешёвая: в сводной таблице результатов колонка или строка
целиком заполнена одним значением (все нули, все максимумы, все «не удалось»). Проверяется
автоматически при построении любой сводки.

**Вопрос-инъекция.** «Все испытуемые дали одинаковый результат — я смотрел СЫРОЙ ответ хотя бы
одного из них, или сужу по баллу? Что меняет исход, если поменять один параметр стенда?»

**Текущая мера.** Правило метода: при одинаковом исходе у всех объектов — (1) открыть сырой ответ,
а не агрегат; (2) поставить решающий эксперимент с одной изменяемой переменной стенда; (3) до
этого не публиковать и не докладывать вывод об объектах. Аудит кода на этом шаге НЕ назначать —
он на этот класс слеп по построению.

**Механический привод определён (2026-08-23, по указанию оператора «фиксируй, это важно»):**
стенд обязан САМ печатать вместе с таблицей блок **«требует толкования»** — вырожденная в
константу колонка/строка, `score=0` при непустом ответе, `eval_tokens=0`/аномальное время,
разброс между повторами при `temperature=0`, поголовный максимум, рост балла после правки
чекера. Прогон не считается завершённым, пока на каждый пункт блока нет письменного ответа;
пустой блок — допустимый исход, неотвеченный пункт — нет. Смысл: вопрос «что это значит»
переносится из дисциплины исполнителя в инструмент, потому что правило-напоминание — мера того
же класса, что «быть внимательнее». Таблица триггеров с провенансом каждого —
`references/llm-benchmark-pitfalls.md`, раздел «Вопрос „что это значит“ — встроить в инструмент».

**Сильнейший из известных приёмов против этого класса — написать вывод для ВНЕШНЕГО читателя**
(оператор, 2026-08-23: «написание статьи — отдельный метод тестирования»). Механизм: аудит
спрашивает «правильно ли сделано», статья — «что это значит»; вырожденный результат безупречен
по коду и разваливается на требовании объяснить ПРИЧИНУ. Приём не требует реальной публикации:
достаточно написать фразу-вывод по каждой строке итоговой таблицы и причину каждого
выделяющегося значения. Фраза, которую нельзя дописать без «наверное», указывает точку, где
надо открыть сырые данные. Развёрнуто, с границами применимости —
`references/llm-benchmark-pitfalls.md`, раздел «Написание статьи как метод тестирования».

**Статус.** OPEN (мера принята 2026-08-23, рецидивов пока нет)
