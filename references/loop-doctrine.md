# §34 Петли — тело правила

**Провенанс:** 2026-08-23. Запрос на переход к петлевому режиму разобран против внешнего
источника по loop engineering → выбран режим добавления: **петли добавляются к доктрине для
повторяемых машинно-проверяемых задач, дисциплина стерильного самоаудита (DOCTRINE-CORE.md §12) остаётся гейтом приёмки**. Требование:
**«использование локальной llm необходимо на всех стадиях. Токены экономим»**. Документ прошёл
три собственных стерильных прогона и независимый внешний аудит — доказательная база в §11,
история ревизий в конце, разбор решений — в журнале контура-владельца (D-050…D-058). Конспект
источника — `loop-engineering-source.md`.

**Документ обезличен:** имена контуров, приборов и проектов сюда не пишутся — только роли
(«владелец петли», «смежный контур», «надзорный контур»). Операционные данные с именами живут в
реестре (`loop-registry.md`, формат — §7) и карточках контуров. «Обезличен» — намеренно не
«стерилен»: стерильность в §5а означает другое (проверяющий не видел работы проверяемого).

## 1. Что такое §34-петля — и три вещи, которые ею НЕ являются

Петля — система, которая сама (1) находит задачу, (2) отдаёт исполнителю, (3) проверяет
результат объективным шлюзом, (4) фиксирует состояние в файле, (5) решает, что дальше,
(6) кладёт результат или эскалацию в оговорённое место и (7) повторяется по расписанию или
событию. Проектируется один раз; дальше работает без человека в роли промптера.

Все семь элементов — ВНУТРИ цикла, на скрипте и Ollama без исключений. «Доклад оператору» — не
восьмой элемент: элемент 6 кладёт файл, а рассказывает о нём Claude ПОТОМ, в обычной сессии,
которую петля не ждёт и не вызывает.

**Границы термина — три соседних механизма, которые §34-петлёй не являются:**

| Механизм | Чем отличается | Что ему нужно вместо §34 |
|---|---|---|
| **`/loop` / `ScheduleWakeup`** (Claude-ведомая работа по расписанию) | Claude ведёт каждый шаг сам («Claude re-runs a prompt» по официальной документации); «локальная LLM на всех стадиях» к нему не относится | обычные правила сессии; в реестр не идёт. `/loop` по прямому поручению оператора легитимен, но это не петля |
| **CI / детерминированный пайплайн без LLM** (push-triggered тесты, задача планировщика) | нет ни одной LLM-стадии — нечего проверять стерильным аудитом и нечем «галлюцинировать» | остаётся CI; карточка и реестр не нужны. **Петля без LLM-стадии — просто автоматизация**, оформлять её по §34 — лишняя бюрократия |
| **Разовый прогон** (даже многочасовой, даже по спеке) | нет повторения по расписанию/событию | лестница делегирования (DOCTRINE-CORE.md §13) |

При регистрации в `<контур>\audit\loops.md` и реестре писать явно **«§34-петля»**, если контекст
допускает путаницу с `/loop`.

**Принцип носителя: петля живёт ВНЕ харнесса.** Все расписания харнесса смертны (факты — §10):
session-scoped, гибнут при `/clear`, recurring истекает через 7 дней сам, пропущенный тик не
догоняется, время срабатывания плавает. Долгоживущая петля — это скрипт в планировщике ОС;
механизмы харнесса годятся только как канал доклада или для короткоживущих (< недели) петель
под присмотром.

## 1а. Четыре принципа конструкции — они, а не перечень правил, порождают §3

Каждое частное правило §3 — следствие одного из четырёх принципов. Новая ситуация, не покрытая
буквой §3, разрешается по принципу, а не по аналогии с соседним пунктом.

1. **Три кольца защиты, каждое ловит то, к чему слепо предыдущее.**
   Кольцо 1 — объективный шлюз (код возврата): структурные дефекты. Слеп к семантике.
   Кольцо 2 — стерильный Ollama-аудит (§5а): правдоподобно-неверный текст, галлюцинация, ответ
   не по существу при зелёном шлюзе. Слеп к неверной постановке задачи.
   Кольцо 3 — человек снаружи (гейт §2, `next_review`, разметка `accepted`): неверная спека,
   устаревший шлюз, расползание прав. Петля без любого из колец — дыра, а не экономия.
2. **Индикатор ставится ПОСЛЕ факта, который он утверждает, и проверяется чтением факта.**
   (Класс C-001; за сутки внедрения дал три живых инцидента.) Следствия: запись `escalated`
   действительна только после `os.path.exists` положенного письма; `outcome` пишется всегда,
   включая падение; выход рождается `accepted: pending`, а не «принят по умолчанию»; метка о
   доставке ставится только реальным ходом получателя.
3. **Механизм без демонстрации не существует.** «Скрипт считает лимиты / проверяет пути / ведёт
   метрику» — пустые слова, пока каждый механизм не показан сработавшим: превысить лимит →
   `stopped_limit`; убрать обязательное поле STATE → падение; записать вне списка путей → отказ;
   оставить 4 неразмеченных выхода → `deferred: unmarked_backlog`. Приёмка петли = демонстрация
   каждого заявленного механизма, той же процедурой, что мутационная проверка шлюза (§3з).
4. **Каждый шаг идемпотентен и переживает обрыв.** Вопрос проектирования: «убьют ровно здесь —
   что сломается при повторном старте?» Результат — во временный файл с атомарным
   переименованием; черновик — с детерминированным именем от входа (повтор перезапишет свой же,
   не наплодит дубликаты); счётчики — вместе с записью результата, не до неё.

## 1б. Кто что делает — роли и их полномочия

Одна таблица закрывает поле «КТО» для всех процедур документа.

| Роль | Кто это | Что делает | Чего НЕ делает |
|---|---|---|---|
| **Владелец петли** | контур, в чьей зоне живёт задача | пишет спеку и скрипт, проходит гейт §2, заполняет карточку, **регистрирует носитель** (`schtasks`/`CronCreate`/хук — своими руками), размечает выходы, проводит `next_review` и все технические проверки (§3з, §5а.4), закрывает петлю | не решает за оператора необратимое; не правит чужие зоны |
| **Claude владельца** | сессия контура | пишет спеку ОДИН раз до петли, принимает эскалации, докладывает оператору | **не работает внутри цикла**; не регистрирует задачу планировщика без явной команды оператора — это изменение системного состояния вне слоя разрешений (§3е) |
| **Надзорный контур** | независимый аудитор, НЕ автор петли | проверяет петли и доктрину, предъявляет находки с провенансом, вправе предписать закрытие | не правит чужой код и чужие карточки сам |
| **Оператор** | человек | закрывает любую петлю без объяснений, разрешает необратимое, снимает ограничения | — |

**Конфликт «владелец возражает — надзор настаивает»:** решает оператор. До его решения петля
**приостанавливается** (`<state>.paused`, §3д): спор о безопасности разрешается в пользу
остановки. Возражение владельца обязано быть фактом (`file:line`, лог, вывод команды).

**Бюджет `next_review`:** «~15 минут» (§6а) — это чтение и решение; технические проверки (§3з,
§5а.4) в него не входят: на холодном старте один вызов модели занимает минуты (§3б), поэтому
реальный бюджет ревью с проверками — от получаса, планируется как отдельная работа.

## 2. Гейт входа — пять пунктов, все обязательны

Задача превращается в петлю ТОЛЬКО если отмечены все пять; иначе остаётся ручным промптом.
(Предусловие ДО гейта — граница термина из §1: есть повторение И есть LLM-стадия.)

| # | Условие | Как проверить фактом |
|---|---|---|
| 1 | Повторяется ≥ 1 раз в неделю | журнал/DECISIONS за месяц показывает ≥4 повтора |
| 2 | **Объективный шлюз** — тест, сборка, линтер, чекер-скрипт — может отклонить результат БЕЗ человека и без модели-«мнения» | команда возвращает ненулевой код на заведомо плохом входе (#SA-3, процедура §3з) |
| 3 | Исполнитель может ЗАПУСТИТЬ результат в своей среде | не «теоретически может», а показано: в ручном прогоне (§3) выполнена команда запуска, её текст и код возврата дословно перенесены в карточку (`gate:`). Для кода «запустить» = собрать И прогнать тест, не только собрать |
| 4 | **Жёсткий стоп**: лимит итераций И времени И Claude-вызовов | записаны в карточке §6 И считаются самим скриптом: итерации — счётчик в STATE; время — сверка elapsed **после каждого элемента** (элемент атомарен, посередине не рвётся) + таймаут одиночного Ollama-вызова (дефолт 600 с); превышение любого → `stopped_limit`. Лимит, который никто не считает, = стоп-условие текстом |
| 5 | Человек перед необратимым: merge, push, deploy, deps, публикация, удаление | необратимое выходит из петли только ЧЕРНОВИКОМ/PR/письмом. Не дублирует §3е, а дополняет: §3е — петля технически НЕ ДЕЛАЕТ таких операций (запрет в коде); п.5 — результат, ведущий к ним, проходит через человека. Первое без второго — петля, которая не пушит сама, но готовит к пушу мусор |

**Плохие петли (не пытаться):** архитектура, авторизация/платежи/финансы, деплой и push,
заключения заказчику, нормативные/метрологические выводы — всё, где «готово» = суждение.

## 3. Сборка: четыре блока, строгий порядок

**Одна автоматизация + одна спека + один файл состояния + один шлюз.** Порядок: надёжный РУЧНОЙ
прогон → оформить спеку → обернуть в петлю → поставить на расписание. Пропуск шага = оплата
системы, которую никто не понимает.

**Спека петли.** Файл `loop-<имя>.spec.md` рядом со скриптом (путь — в карточке §6). Содержит
всё, что Ollama-стадиям нужно для работы без Claude: правила классификации с примерами
(«таймаут → повтор 1 раз; трейсбек с нашим модулем → черновик фикса; чужой модуль →
эскалация»), шаблон черновика/письма, списки паттернов, явные запреты. Скрипт **перечитывает
спеку каждый прогон** и вставляет в промпт Ollama-стадий целиком — это и есть защита от дрейфа
цели (§5). Правка спеки = правка петли: повторить демонстрацию затронутых механизмов (§1а.3),
обновить `mechanisms-demoed`.

## 3а. Носитель триггера

`cron` на Windows нет; выбор из трёх, по убыванию предпочтительности:

| Носитель | Когда брать | Ограничение (факты — §10) |
|---|---|---|
| **Планировщик ОС** (`schtasks`) → `.ps1`/`.py` | дефолт для любой петли | сам решает конфликты ресурсов (§3б) |
| **`CronCreate`** харнесса | нужен ход Claude по расписанию И петля живёт < недели под присмотром | session-scoped: гибнет при `/clear`, recurring истекает через 7 дней, пропуски не догоняются, jitter до 30 мин, внешний выключатель `CLAUDE_CODE_DISABLE_CRON`. Каждый ход платный |
| **Хук** (`SessionStart`/`UserPromptSubmit`) | триггер по событию, не по времени | в чужом ходе: быстрым (<10 с), молчаливым без находок. `SessionStart` срабатывает на `startup/resume/clear/compact/fork` — в т.ч. БЕЗ человека; хук, меняющий состояние, обязан различать `source` |

Регистрация — командой, не через GUI; в карточку идёт та строка, которой петля реально заведена:

```powershell
# 1. Планировщик ОС (дефолт). Проверка: schtasks /Query /TN "loop-<имя>" /V
schtasks /Create /TN "loop-<имя>" /TR "powershell -NoProfile -File <абс. путь>\loop_<имя>.ps1" /SC DAILY /ST 03:17
```
```
# 2. CronCreate (только петли < недели): CronCreate(schedule="17 3 * * *", prompt="…", recurring=true)
#    Проверка: CronList → 8-символьный id; снятие: CronDelete(<id>)
```
```json
// 3. Хук: в settings.json; скрипт ОБЯЗАН читать hook_event_name/source и молча выходить
// на неподходящем (иначе сработает на compact/resume без участия человека)
{"hooks": {"SessionStart": [{"hooks": [{"type": "command",
  "command": "python <абс. путь>\\loop_<имя>_hook.py", "timeout": 10}]}]}}
```
(Минута не `:00`/`:30` — уводит от jitter-окна харнесса, §10.)

## 3б. Общие ресурсы: GPU, файлы, параллельные прогоны

Ollama — **общий ресурс с оператором и другими контурами**, не собственность петли:

- Перед серией — `GET /api/ps`: чужая модель загружена → НЕ выгружать (`keep_alive=0` вырывает
  карту у оператора из-под рук), отложить прогон, `deferred: gpu_busy` в STATE.
- Один прогон — один файл результата (параллельная запись портит данные молча). Лок-файл
  `<state>.lock` с PID и временем; чужой живой лок → `deferred: already_running`.
- Протухший лок (PID мёртв) снимается автоматически, факт снятия — в STATE.
- Петля НИКОГДА не убивает чужие процессы Ollama и не перезапускает службу.
- **Холодный старт — минуты, и это норма.** Первый вызов после простоя грузит веса в VRAM:
  для модели ~19 ГБ измерено **288 с против 20–24 с** при уже загруженной (×12). Следствия:
  (а) Ollama-стадии одного прогона идут **подряд**, не размазываются по времени; (б) порог
  «аномально долго» (§4) не применяется к первому вызову; (в) холодный старт закладывается в
  бюджет `time=` жёсткого стопа — иначе петля штатно выбивает лимит первым же вызовом.

## 3в. Файл состояния (STATE) — единый формат

JSON рядом с человекочитаемым `.md`, либо `.md` с YAML-шапкой. Обязательные поля:

```json
{
  "loop": "<имя>", "owner": "<контур>",
  "last_run": {"started": "<ISO>", "finished": "<ISO|null>", "outcome": "ok|gate_failed|deferred|stopped_limit|error"},
  "last_success": "<ISO>",
  "in_progress": [{"item": "<что>", "since": "<ISO>"}],
  "escalated": [{"item": "<что>", "why": "<причина>", "when": "<ISO>", "to": "<адресат>", "resolved": "<ISO|null>"}],
  "counters": {"runs_30d": 0, "accepted_30d": 0, "rejected_30d": 0, "unmarked": 0, "stale_escalated": 0},
  "retries": {"<стадия>": {"count": 0, "last_reason": "<причина>"}},
  "next_review": "<YYYY-MM-DD>",
  "lessons": ["<ожидал X → оказалось Y → обход Z>"]
}
```

- `outcome` пишется всегда, включая падение: «прогон был и упал» ценнее отсутствия записи.
- Непустой `in_progress` при `finished != null` = аварийный обрыв; следующий прогон обязан
  заметить и либо повторить элемент (шаги идемпотентны — §1а.4), либо эскалировать.
- Счётчики считаются **по-элементно, не только суммарно**: агрегат маскирует аномалию одного
  компонента.
- `lessons` — как практика фиксации уроков в других частях доктрины: урок в файл, не в потерянный лог.
- **`retries` — счётчик, не запись причины.** Скрипт инкрементирует `count` ПЕРЕД повтором;
  `count > 2` → повтор не делается, стадия завершается эскалацией. Сброс — только при успехе
  стадии, не при новом прогоне (иначе «≤2» обходится перезапуском петли).
- `counters` — не инкрементальные числа, а ПЕРЕСЧЁТ из `runs.jsonl` (§6а) при каждом старте:
  пересчитываемое из журнала нельзя испортить сбоем счётчика.

## 3г. Идемпотентность — см. принцип §1а.4

Проверяется на приёмке демонстрацией (§1а.3): убить прогон на середине записи → повторный старт
не дублирует и не портит.

## 3д. Остановка и пауза — без правки кода

- Файл-стоп `<state>.paused` → петля стартует, видит, выходит с `deferred: paused`. Дефолт.
- Снятие задачи: `schtasks /Delete /TN "loop-<имя>" /F` либо `CronDelete`.
- Аварийно: снять процесс по PID из лок-файла, удалить лок вручную.

Оператор останавливает любую петлю одной операцией, зная только имя.

## 3е. Границы прав: петля работает ВНЕ слоя разрешений

Скрипт планировщика и хук выполняются без ask-гейта — слой разрешений Claude к ним не
применяется вообще. Компенсация:

- **Минимальные права, обеспеченные кодом**: все пути записи перечислены в карточке явным
  списком; скрипт в начале прогона сверяет каждый путь записи со списком и падает при выходе за
  него. Честная граница: под Windows настоящей песочницы нет — ограничение живёт в коде петли.
- Никаких `git push`, публикаций, удалений, установки зависимостей — даже если «технически
  может». §2 п.5 — компенсация отсутствующего гейта, не пожелание.
- **Запрет распространяется на ОПОСРЕДОВАННОЕ действие**: нельзя класть выход туда, откуда его
  подхватит сторонний автоматический процесс — в ветку с авто-мержем, в каталог с внешней
  синхронизацией, в очередь чужого демона. Формально «петля не пушит», фактически push
  происходит без человека. Проверка при заполнении карточки — поле `write-paths-readers`: для
  каждого пути записи ответить, **кто читает его автоматически**; если кто-то читает и
  действует — путь запрещён.
- Токены/ключи петле не выдаются; нужен внешний сервис → эскалация, не сохранённый credential.
- На каждом `next_review` выданные «на один раз» права либо обосновываются заново, либо
  снимаются.

## 3ж. Эскалация — с фактической доставкой

1. Причина в STATE (`escalated[]`) — всегда.
2. Письмо файлом в `_interchat\inbox\<владелец петли>\` по конвенции
   `YYYYMMDD-HHMMSS_from-loop-<имя>_<slug>.md`: что пыталась, на чём встала, что проверено,
   чего НЕ делала. **Эскалация состоялась, только когда файл существует** — скрипт проверяет
   `os.path.exists` после записи (§1а.2); не записалось → `outcome: "error"`.
3. Ничего не ждёт ответа в цикле: прогон завершается; следующий старт видит незакрытый
   `escalated[]` и не повторяет тот же элемент.
4. **Снятие:** владелец, разобрав письмо, проставляет элементу `resolved: <ISO>` в STATE.
   Элементы с `resolved` скрипт не трогает; без `resolved` — не перерабатывает и повторно НЕ
   эскалирует (иначе ящик засоряется одинаковыми письмами — «шумная автоматика, которую
   перестают читать»).
5. **Устаревание — симметрично неразмеченным выходам:** эскалация без `resolved` старше
   `stale_escalation_days` (карточка, дефолт 7) идёт в `counters.stale_escalated`; при
   `stale_escalated > 0` каждый прогон завершается `deferred: stale_escalation` вместо новой
   работы — пока прошлое непонятное не разобрано, накапливать новое бессмысленно.

## 3з. Мутационная проверка шлюза — процедура

1. Копия артефакта в scratchpad **по абсолютному пути** (не `/tmp`: в Git Bash и Windows-Python
   это разные каталоги).
2. Мутация ломает именно тот класс, который шлюз обязан ловить; мутатор содержит
   `assert <образец> in <текст>` — непроведённая мутация обрывает проверку.
3. Шаги соединять `&&`, никогда `;` — падение мутатора не должно пропускать прогон дальше.
4. Шлюз на мутанте → обязан вернуть ненулевой код; зелёный здесь = шлюз негоден, петли нет.
5. Откат → шлюз на чистом обязан вернуть 0 (иначе красит всё подряд и так же бесполезен).
6. Дата и ЧЕМ ломали — в карточку (`mutation-checked`).

Проводится **до первого запуска**, повторяется при изменении шлюза и на каждом `next_review`.
Той же процедурой демонстрируются остальные механизмы (§1а.3); проверка стерильного аудитора —
отдельно в §5а.4: «умеет краснеть» для аудитора значит иное, чем для шлюза.

## 3и. Выход петли — формат, место, разметка

«Оговорённое место» из §1 элемента 6 — конкретно:

- **Каталог выходов** `out\` рядом со STATE (входит в `write-paths`). Один выход — один файл
  `YYYYMMDD-HHMMSS_<slug>.md`; slug детерминирован от входного элемента (§1а.4 — повтор
  перезаписывает свой же файл).
- **YAML-шапка выхода** (без неё разметка §6а невозможна):
  ```yaml
  loop: <имя>
  item: <входной элемент, по которому сделан выход>
  created: <ISO>
  accepted: pending   # владелец меняет на yes / no при разборе
  ```
- **Разметка:** владелец меняет `accepted: pending` на `yes`/`no` — одна правка одной строки.
  Эскалационные письма размечаются так же, но живут в inbox.
- Создание выхода и его разметка **дописываются в `runs.jsonl`** — счётчик `unmarked` считается
  по журналу, не сканом каталога (механика и почему — §6а). Каталог `out\` можно чистить и
  архивировать; журнал — нельзя.

## 4. Стадии и носители — Claude вне цикла

| Стадия | Носитель | Claude |
|---|---|---|
| Триггер / расписание | планировщик ОС / хук (§3а) | нет |
| Поиск задачи (скан логов, CI, inbox, диффов) | скрипт → Ollama для классификации | нет |
| Исполнение (черновик правки/теста/саммари/письма) | Ollama через `guarded_generate()` — импорт по абсолютному пути к скиллу-донору (механика переиспользования — DOCTRINE-CORE.md §13, ступень −1 «проверить, нет ли готового»: `sys.path.insert(0, r"<путь к скиллу workflow>\scripts")` → `from vram_guard_reference import guarded_generate`); крупный код — Claude пишет СПЕКУ один раз ДО петли, генерирует Ollama, приёмка с мутационной проверкой | **нет** — задача, требующая суждения по ходу, в петлю не входит (§2) |
| Шлюз | объективная команда — она одна решает pass/fail. Плюс кольцо 2 (§5а) при человекочитаемом выходе | нет |
| Фиксация состояния | скрипт; Ollama суммирует логи >200 строк | нет |
| Решение «что дальше» / эскалация | скрипт по правилам спеки (§3); неясное → эскалация (§3ж) | только адресат эскалации |
| Доклад оператору | — (вне цикла, §1) | Claude, потом, по STATE |

**Отказ импорта — отдельный класс, не «отказ Ollama».** Путь к донору может умереть (скилл
переехал, junction битый, другой Python). Скрипт оборачивает импорт в `try/except ImportError`
и при неудаче завершается `outcome: "error"` + эскалация «донор недоступен, путь такой-то» — а
НЕ подставляет локальный дубликат `guarded_generate` (копия разойдётся с оригиналом — DOCTRINE-CORE.md §13, ступень −1).
Демонстрация (§1а.3): временно переименовать каталог донора → петля падает с внятной
эскалацией, не с трейсбеком в пустоту.

**Отказы Ollama.** HTTP/timeout/JSON/пусто — не бесконечный retry: ≤2 повтора (счётчик
`retries` в STATE — §3в) → `ollama_failure` + эскалация; падение Ollama НЕ поднимает стадию на
Claude автоматически. **Тихий отказ**: пустой ответ за аномально короткое время — не «находок
нет», а сбой (измерено: та же линза на том же входе — 0 находок за 2,2 с и 8 за 15,5 с при
`temperature=0`). Один повтор; ноль, воспроизведённый повтором, — честный результат.

**Аномалия времени — в обе стороны.** Слишком быстро — тихий отказ (выше). Слишком долго —
зацикливание модели ЛИБО холодный старт (§3б); различает их не время, а результат: валидный
проверяемый выход при долгом ответе = загрузка весов, поток мусора без завершения =
зацикливание. Порог — **относительно медианы остальных вызовов того же прогона** (сам
проверяемый вызов в медиану не входит — иначе выброс маскирует себя), к первому вызову серии
не применяется.

## 5а. Стерильный Ollama-аудит — кольцо 2, дисциплина самоаудита (DOCTRINE-CORE.md §12) без Claude

Раз Claude внутри петли не работает, роль стерильного прохода из DOCTRINE-CORE.md §12 исполняет **отдельный вызов
Ollama** — по тем же правилам, что стерильный проход у Claude. Стерильность — свойство ПРОМПТА
и ВЫЗОВА, а не намерения: она либо обеспечена механически, либо её нет.

### 5а.1. Механика вызова

- **Только `/api/generate`, поле `context` не передаётся** (иначе Ollama дотянет состояние
  прошлого вызова). `/api/chat` с накопленным `messages` для аудита запрещён по построению.
- Аудитор — **отдельный вызов**, не «второе сообщение в переписке». Общее у стадий — только
  файл, никогда не объект разговора.
- `temperature=0` — вердикт воспроизводим; разброс при нулевой температуре сам по себе аномалия.
- `num_ctx` — ЯВНО и с запасом: молчаливая обрезка отбрасывает ГОЛОВУ промпта, то есть саму
  инструкцию аудитора, а вердикт приходит бодрый и пустой.
- `keep_alive=0` к стерильности отношения НЕ имеет (это выгрузка весов из VRAM) и в общей
  среде вредит (§3б).

### 5а.2. Что НЕЛЬЗЯ класть в промпт аудитора — закрытый список

Каждый пункт — способ превратить проверку в подтверждение:

| Запрещено | Почему |
|---|---|
| Рассуждения/черновые мысли исполнителя | аудитор наследует его логику вместе с ошибкой |
| «Исполнитель считает, что…», «подтверди…», «убедись, что всё верно» | названный ответ подтверждают, а не проверяют |
| Ожидаемый результат в любом виде («должно быть 3 находки», «ожидается PASS») | превращает аудит в подгонку |
| Вердикт первого прохода при двух проходах | второй проход перестаёт быть независимым |
| `lessons[]`, история прошлых прогонов и вердиктов | подсказка «где искать» = слепота ко всему остальному |
| **Спека петли целиком** | спека — то, по чему работал исполнитель; аудитор с ней наследует его слепые пятна и терминологию. Аудитору даётся **критерий приёмки, переформулированный независимо** |

Разрешено и необходимо: проверяемый артефакт, исходные данные (входной элемент), критерий
приёмки своими словами, требуемый формат ответа.

### 5а.3. Шаблон брифа (заполнять, не изобретать)

```
Ты проверяешь готовый артефакт. Ты не видел, как он создавался, и не должен ни с кем соглашаться.

ЗАДАЧА, которая ставилась: <одно предложение, независимая формулировка>
КРИТЕРИЙ ПРИЁМКИ: <проверяемые условия списком; без слов «должно получиться …»>

Проверь артефакт против критерия. Каждое замечание обязано указывать конкретное место
(строку/фрагмент). Если артефакт критерию соответствует — так и скажи, это нормальный исход.

Ответ строго JSON: {"verdict":"pass|fail","findings":[{"quote":"<дословно из артефакта>",
"problem":"<в чём расхождение с критерием>"}]}

АРТЕФАКТ:
<текст>
```

### 5а.4. Проверка самого аудитора — обязательна, как мутационная проверка шлюза

**Аудитор — такой же механизм, как шлюз, и по §1а.3 не существует, пока не показан
сработавшим.** Аудитор, который всё подтверждает, — Ralph Wiggum этажом выше. Процедура
(до первого запуска и на каждом `next_review`):

1. **Отрицательный контроль:** заведомо ПЛОХОЙ артефакт того же класса → обязан `fail` с
   указанием места. `pass` здесь = аудитор негоден. Дефект для контроля берётся **из целевого
   класса аудитора** — не «пустой файл», а правдоподобный текст с фактической ошибкой, ровно
   то, к чему слеп объективный шлюз: все проверки формально проходятся с намеренно узким
   критерием («файл непустой»), и получается исправный по механике, но слепой по содержанию
   аудитор. Если критерий не позволяет сформулировать такой дефект — проблема в критерии.
2. **Положительный контроль:** заведомо хороший артефакт → обязан `pass`. Вечный `fail` так же
   бесполезен, как вечный `pass` — владелец перестанет читать.
3. **Дословность цитат:** `quote` из находок реально встречается в артефакте — сравнение со
   снятием разметки и нормализацией типографики, иначе меряется форма, а не содержание.
4. **Тест на подсказку** (если исполнитель и аудитор — одна модель): дать аудитору плохой
   артефакт, СОЗДАННЫЙ этой же моделью. Подтвердил свой брак — self-preference подтверждён
   фактом: нужна другая модель либо явная фиксация ограничения в карточке.
5. Дата и содержание — в карточку, поле `checker-verified`.

### 5а.5. Когда одна модель на всё — честный обходной путь

Парк бывает узким (вплоть до одной пригодной модели). Тогда «другая модель» недостижима, и
стерильность держится только на чистоте контекста:
- записать в карточку `sterile: контекст (одна модель — другой в парке нет)`;
- обязательно выполнить §5а.4 п.4 и записать результат;
- поднять `passes` до 2 с **разными формулировками критерия** — слабее двух моделей, но
  сильнее одного прохода;
- при появлении второй пригодной модели — вернуться и переставить.

Скрывать ограничение нельзя: непроверенная стерильность хуже честно названной слабой.

### 5а.6. Логирование аудита — иначе стерильность недоказуема

Каждый вызов аудитора сохраняется рядом с выходом: `out\<slug>.audit.json` с полями
`prompt_sha256`, `model`, `temperature`, `num_ctx`, `verdict`, `findings`, `seconds`. Хеш
промпта, а не промпт целиком; при разборе спорного случая скрипт обязан уметь воспроизвести
промпт из артефакта и брифа — иначе доказать, что в промпт не попало лишнее, невозможно.
Аномалии (`fail` без находок, пустой ответ, время меньше порога — §4) поднимают тот же вопрос,
что и в шлюзе: сбой или результат.

### 5а.7. Когда обязателен и сколько проходов

**Обязателен** для ЛЮБОГО выхода петли, который дальше читает человек (черновик, PR, письмо,
саммари). Чисто бинарный шлюз без человекочитаемого выхода может обойтись без него.

**Два прохода, а не один** — выход удовлетворяет хотя бы одному из трёх критериев: (а) уходит
ЗА пределы контура-владельца (оператору, смежному контуру, во внешний PR); (б) касается денег,
метрологии, дозиметрии или безопасности; (в) предлагает правку чужой зоны. Внутренний черновик
для самого владельца — один проход. Проходы не видят друг друга и результатов друг друга
(§5а.2); **расхождение вердиктов = эскалация**, не «выбрать лучший» и не «два из трёх».

**Граница кольца:** аудит ловит расхождение с ЗАДАННОЙ задачей; от неверно заданной задачи
защищает только кольцо 3. Человекочитаемый выход без стерильного аудита = петля не
запускается, тем же порядком, что без карточки.

## 6а. Метрика и смерть петли — штатный исход, не провал

- **Считает скрипт, не человек по памяти.** Каждый прогон дописывает строку в append-only
  журнал `runs.jsonl` рядом со STATE (`{started, finished, outcome, items, accepted,
  rejected}`); создание выхода — `{"kind":"output","slug":…,"created":…}`, разметка владельца —
  `{"kind":"mark","slug":…,"accepted":"yes|no","when":…}`. `counters` в STATE — пересчёт из
  журнала при каждом старте фильтром «последние 30 суток».
- **`unmarked` = число `output`-строк старше 24 ч без соответствующей `mark`-строки.** Именно
  по журналу, не сканом каталога: единственный автостоп петли иначе обходится переносом
  `pending`-файлов в архив. Удаление файла из `out\` счётчик НЕ уменьшает — журнал append-only;
  файл пропал, а `mark` не появилась — это `unmarked`, и петля встанет ровно так же. Роли
  разведены: каталог хранит содержимое (можно чистить), журнал — факт (нельзя).
- **`accepted`** = владелец принял без переделки по существу. Переделанный, отклонённый или
  пролежавший непрочитанным до следующего прогона — `rejected`.
- **Привод разметки** (§1а.2): выход рождается `accepted: pending`; при
  `unmarked > unmarked_limit` (дефолт 3) новый прогон не начинается — `deferred:
  unmarked_backlog` + одно письмо владельцу (одно, не на каждый прогон — §3ж п.4). Петля, чьи
  результаты никто не размечает, останавливается сама.
- **Поводы закрыть петлю, равносильные:** `accepted/total < 0,5` за 30 дней · ни одной снятой
  пометки за 30 дней · просроченный `next_review` без проверки · падение отдачи, установленное
  владельцем (прецедент: кривая находок 4→1→2→3→2→0 — остановка по отдаче, до всякой метрики).
- **При <0,5 сначала вопрос, не тюнинг:** петля плохо работает — или задача не подходила под
  петлю (§2)? Второе — частый случай; тогда закрытие.
- **Процедура `next_review`** (владелец, ~15 минут на чтение и решение; технические проверки —
  отдельно, §1б; выполненное ревью = все четыре пункта):
  1. Мутационная проверка шлюза повторена (§3з), дата обновлена в `mutation-checked`.
  2. Права и `write-paths` пересмотрены: выданное «на один раз» обосновано заново или снято.
  3. Прочитана выборка выходов: минимум 3 последних (или все, если меньше) — глазами, не
     пересказом; вопрос при чтении: «шлюз и аудит всё ещё ловят то, ради чего ставились?»
  4. Метрика прочитана, решение записано строкой `reviewed: <дата> → продолжить | закрыть
     (<причина>)`; при «продолжить» `next_review` сдвигается на +30 дней.
- **Кто закрывает:** владелец — решением; надзорный контур — предписанием (владелец исполняет
  либо возражает фактом; конфликт — §1б); оператор — всегда. Технически закрытие = файл-стоп +
  снятие задачи планировщика + статус в реестре с причиной. Карточка остаётся в
  `audit\loops.md` как история; STATE и `runs.jsonl` не удаляются.

## 6б. Сквозной пример: минимальная §34-петля

Учебный, показывает связность блоков.

**Задача:** раз в сутки проверять скиллы на незаскрабленный персональный путь, при находке
готовить письмо владельцу.

1. **Ручной прогон** (§3): grep-проверки руками, коды возврата подтверждены.
2. **Шлюз:** `grep -rlI 'Users[\\/]<профиль>[\\/]' <путь> --include='*.md'` → код 1 = чисто.
   Мутационная проверка (§3з): вставить путь в копию → 0 (находка); убрать → 1. Дата в карточку.
3. **Носитель** (§3а): планировщик ОС, ежедневно 03:17, `loop_scrub.ps1`. Claude не пробуждается.
4. **Стадии** (§4): поиск — grep; классификация «утечка/ложное» — Ollama; черновик письма —
   Ollama; **стерильный аудит черновика** (§5а) — отдельный вызов другой модели по шаблону
   §5а.3, без спеки и рассуждений исполнителя (§5а.2); аудитор заранее проверен по §5а.4:
   черновик со ссылкой на несуществующий файл → `fail`, корректный → `pass`; STATE — скрипт.
5. **STATE** (§3в) + лок (§3б) + журнал `runs.jsonl` (§6а).
6. **Необратимое** (§2 п.5): петля не правит скиллы и не пушит — только письмо в inbox (§3ж).
7. **Стоп:** `iterations=1`, `time=10 мин` (с запасом на холодный старт — §3б), `claude_calls=0`.
8. **Карточка** (§6) целиком; строка в реестр со статусом «реализована». Только теперь — на
   расписание.

## 7. Реестр петель — формат, словарь статусов, место

Реестр ведётся **вне этого документа**: `references/loop-registry.md`, append-only, строка на
петлю. Реестр отражает **весь жизненный цикл**, а не только работающие петли: предложения и
отказы — тоже информация (отказ с причиной предотвращает повторное предложение того же).

**Словарь статусов (закрытый; решение оператора делегировано владельцу доктрины 2026-08-24):**

| Статус | Что означает | Когда присваивается |
|---|---|---|
| `предложена` | кандидат назван, решения владельца нет | при рассылке/идее |
| `принята (карточка в работе)` | владелец взял, карточка §6 не заполнена | по слову владельца |
| `реализована (триггер: да/нет)` | **карточка §6 заполнена целиком** — без этого статус запрещён; триггер может быть сознательно не настроен | после карточки и демонстраций |
| `приостановлена` | `<state>.paused`, причина в реестре | по §3д |
| `закрыта (причина, дата)` | метрика/ревью/решение — §6а | при закрытии |
| `отклонена (причина, дата)` | владелец показал фактом, что гейт §2 не проходит | терминальный, уважаемый исход |

Инвариант прежнего правила «строка не раньше карточки» сохранён там, где он осмыслен: **статус
`реализована` без полной карточки невозможен**. Ранние статусы карточки не требуют. Из реестра
ничего не удаляется — статусы только меняются; закрытые и отклонённые строки остаются с
причинами.

## 8. Пригодность по типам работ

Не список контуров, а классы задач — сопоставлять со своим предметом самостоятельно:

| Тип работы | Пригодность | Типичный шлюз |
|---|---|---|
| Сборка/прошивка по расписанию, регрессия на эталонах | высокая | компилятор, тест, сравнение с эталоном (с допуском по статистике, если объект случайный) |
| Регрессия прикладного ПО, разбор падений тестов | высокая | тест-раннер, код возврата |
| Гигиена репозиториев и конфигураций (сканы утечек, счётчики расхождений) | высокая | `grep`/линтер с кодом возврата; результат — письмо, не правка |
| Измерительные стенды и их поверка | средняя: годится прогон, НЕ годится интерпретация результата | чекер-скрипт, оракул |
| Научные расчёты с суждением о физике/нормативе | низкая | шлюза нет — «готово» = суждение (§2) |
| Заключения заказчику, архитектура, платежи | **непригодно** | — |

Отдельный сигнал: если риск, ради которого заводится петля, **уже закрыт обычным CI** — петля
не нужна (§1, границы термина).

## 9. Отношение к дисциплине самоаудита и делегирования (DOCTRINE-CORE.md §12/§13)

Ортогональны: петля — ГДЕ и КОГДА запускается работа и ЧЕМ принимается внутри цикла; дисциплина
самоаудита (§12) — КАК результат принимается оператором. Лестница делегирования (§13) внутри петли работает как обычно:
скрипт → Ollama → субагент; веер/`Workflow` в петле — только по явной команде оператора.
Стерильный аудит §5а — транспозиция дисциплины самоаудита (§12) внутрь цикла; кольцо 3 — та же дисциплина снаружи.

## 10. Сверка с официальной документацией харнесса (2026-08-24)

Читано напрямую (`code.claude.com/docs/en/scheduled-tasks`, `/hooks`, `/sub-agents`), не по
памяти модели. Только то, что меняет или подтверждает наши правила:

| Документация | Следствие для петель |
|---|---|
| `/loop`/`CronCreate` session-scoped: гибнут при `/clear`; recurring истекает через **7 дней** сам; пропуски не догоняются | харнесс не даёт долгоживущей петли в принципе → принцип носителя §1; 7-дневный лимит — осознанная защита («bounds how long a forgotten loop can run»), `next_review` её дополняет |
| `/loop` без интервала = Claude сам выбирает паузу (`ScheduleWakeup`) | Claude-ведомый механизм, не §34-петля — развилка §1 подтверждена источником |
| `SessionStart` fires on `startup/resume/clear/compact/fork` | хук обязан различать `source`; на `compact` срабатывает без человека |
| Fires «between turns», при занятости ждёт конца хода; jitter до 30 мин | точное время старта на харнесе не гарантируется; для точного окна — планировщик ОС, минута не `:00`/`:30` |
| `CLAUDE_CODE_DISABLE_CRON=1` отключает всё | у харнесс-носителя есть внешний выключатель; носитель в карточке указывать явно |
| Субагенты: свой контекст, возвращают итог; `isolation: worktree` | совпадает с лестницей делегирования (§13), ступень 3; отдельного правила не требует |

**Вывод:** прямых противоречий нет. «Claude вне цикла» подтверждается от противного: `/loop` и
`CronCreate` по конструкции вызывают ход Claude — именно поэтому они не основной носитель.
