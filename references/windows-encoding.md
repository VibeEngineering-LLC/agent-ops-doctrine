## Среда оператора (constant)

- Windows 11, primary codepage cp1251 (русская локаль).
- Shell — PowerShell / cmd, по умолчанию stdout = cp1251.
- Все рабочие файлы, имена путей, ввод/вывод — **по-русски**, регулярно содержат
  кириллицу + спецсимволы (`→`, `≈`, `±`, `Δ`, `≥`, `✓`, `×`, греческие буквы,
  стрелки, математика).
- cp1251 НЕ покрывает большинство этих символов → silent или loud
  `UnicodeEncodeError` посреди скрипта.

---

## Правило (HARD)

Любой запуск Python через Bash, который **печатает или читает** не-ASCII символы
(кириллица, греческие, стрелки, математические знаки) — ОБЯЗАТЕЛЬНО префиксуется
`PYTHONIOENCODING=utf-8`:

```bash
# PowerShell:
$env:PYTHONIOENCODING='utf-8'; python -c "..."

# cmd / Bash tool (предпочтительно):
set PYTHONIOENCODING=utf-8 && python -c "..."

# Bash one-liner:
PYTHONIOENCODING=utf-8 python -c "..."
```

Эквивалентно — внутри скрипта первой строкой:
```python
import sys; sys.stdout.reconfigure(encoding='utf-8')
```

## Применять ВСЕГДА когда

1. Скрипт парсит файлы с русскими именами / содержимым (LSRM `.spe`, любые
   проектные данные оператора).
2. `print()` содержит кириллицу или математические символы (→ ≈ Δ ≥ × ÷ ± μ σ
   греческие, стрелки, ✓ ✗).
3. Скрипт читает stdin с не-ASCII.
4. Файл записывается на диск — добавлять `encoding='utf-8'` к `open()` /
   `Path.write_text()` / `json.dump` (через `ensure_ascii=False`).

**Не учитывать ТОЛЬКО если** скрипт строго ASCII на входе и выходе — но
по умолчанию **считать что не ASCII**, на машине оператора это норма.

**Дополнительно** — когда нужно красивое форматирование с Unicode:
- Use `\N{NAME}` нотацию в Python для самодокументации (`'\N{RIGHTWARDS ARROW}'`)
  если опасно для cp1251 без shim.
- Или fallback на ASCII: `->` вместо `→`, `~=` вместо `≈`, `delta` вместо `Δ`,
  но только если оператор явно не ждёт типографики.

## PowerShell-СКРИПТЫ (`.ps1`) — ASCII-only СРАЗУ, не «после первой ошибки»

**Зафиксировано оператором 2026-08-15 дословно: «запиши — сразу делать нормально».**
Триггер: писал `.ps1` с русскими `Write-Output` через Write tool (UTF-8 без BOM),
`powershell -File` прочитал его как cp1251 → мусор `"�?� �?�"�?�>�?����"` внутри
строки, `ParserError: UnexpectedToken`, скрипт даже не стартовал. Пришлось
переписывать и запускать второй раз — ровно та потеря прогона, ради которой это
правило и существует.

**ИМПЕРАТИВ:** любой `.ps1`, который я пишу через Write/Edit и запускаю через
`powershell -File`, — **сообщения и комментарии ТОЛЬКО ASCII, с первой попытки**.
Не «напишу по-русски, если сломается — исправлю»: сломается всегда, это не
вероятность, а свойство среды (Windows PowerShell 5.1 читает `.ps1` без BOM в
кодировке ANSI/cp1251, не в UTF-8).

| Что | Как |
|---|---|
| `Write-Output` / `Write-Host` в `.ps1` | ASCII: `"found: 30"`, `"lowered: 30, failed: 0"` |
| Комментарии в `.ps1` | ASCII |
| Кириллица В ПУТЯХ внутри `.ps1` | допустима только если файл записан **UTF-8 с BOM** (тогда PS 5.1 распознаёт кодировку) либо через `pwsh` 7+ (тот читает UTF-8 по умолчанию) |
| Русский текст оператору | НЕ в `.ps1` — печатать из Python (там `PYTHONIOENCODING=utf-8` решает) либо отдавать мне на вывод в чат |

**Три рабочих способа, если русский текст в `.ps1` реально нужен:**
1. `mcp__pwsh__pwsh` (§27, скилл `dev-env`) — persistent UTF-8-канал, mojibake нет by design. **Дефолт для кириллицы.**
2. Записать `.ps1` **UTF-8 с BOM**: `[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding $true))`.
3. Запускать через `pwsh` (PowerShell 7+), а не `powershell` (5.1).

**Anti-pattern (мой, 15.08):** написал `.ps1` с русскими сообщениями → ParserError →
переписал в ASCII → запустил заново. Второй запуск был не нужен: правило было
известно (§2 про Python), но не перенесено на `.ps1`. Теперь перенесено.

## STDIN — форсировать UTF-8 СИММЕТРИЧНО со stdout (FR-006, 2026-08-15)

**Триггер:** PreCompact-хук `compact-guard` форсировал UTF-8 только на `sys.stdout`.
`sys.stdin.read()` на cp1251-консоли декодировал JSON-payload от Claude Code не тем
кодеком → кириллица в `cwd` (`…\надзорный`) стала суррогатами → `UnicodeEncodeError:
surrogates not allowed` при записи файла → ковталось широким `except` → **exit=0,
файл 0 байт, никакого признака сбоя**. Полный разбор: `надзорный\audit\failure-register.md`, FR-006.

**ИМПЕРАТИВ:** правило §2 действует НА ОБА направления. Скрипт, который читает
не-ASCII со stdin, обязан закрыть вход, а не только выход.

| Случай | Как правильно |
|---|---|
| **Хук Claude Code** (payload JSON на stdin) | `raw = sys.stdin.buffer.read()` → `json.loads(raw.decode("utf-8", errors="replace"))`. Байты, не текст — не зависит от кодировки консоли вообще |
| Обычный скрипт, читающий stdin | `sys.stdin.reconfigure(encoding="utf-8", errors="replace")` сразу после `stdout.reconfigure` |
| Запуск через Bash | `PYTHONIOENCODING=utf-8` покрывает stdin и stdout сразу |

**Anti-patterns:**
- ❌ `json.load(sys.stdin)` в хуке на этой машине — текстовый режим, кодировка консоли.
- ❌ `sys.stdout.reconfigure(...)` без парного `stdin` там, где stdin читается.
- ❌ Широкий `except`, глотающий `UnicodeEncodeError`, без записи traceback — сбой
  становится невидимым; отладка возможна только патчем debug-копии.
- ❌ Починить один файл и не проверить остальные того же класса. По FR-006 после фикса
  нашлось **ещё 5 хуков** с тем же дефектом; худший (`session_start_hook.py`) сверяет
  `cwd` с маркером `"надзорный"` — при битой кириллице контур молча не распознаётся.

## Carve-out (когда ASCII fallback оправдан)

- Debug-логи / progress-сообщения в Bash → можно `->`, `<=`, `delta`, `R2` — это
  читает оператор по факту прогона, типографика не критична.
- Финальный артефакт (отчёт, JSON, виджет) → ВСЕГДА UTF-8 + Unicode-типографика,
  без компромиссов.

---

## Не делать (anti-patterns)

- ❌ `print('Δ=...')` без `PYTHONIOENCODING=utf-8` → краш посреди скрипта,
  потеря всего progress'a stdout после крашевшейся строки (расчёты уже прошли,
  но видим только до неё).
- ❌ `open(path, 'w')` без `encoding='utf-8'` на текстовом файле с кириллицей →
  cp1251 запись, потом нечитаемо в редакторе с UTF-8.
- ❌ `json.dump(d, f)` без `ensure_ascii=False` → русские строки превращаются
  в escape-последовательности, нечитаемо глазом.

## Связь с правилом делегирования

Subagent-брифы для задач с русскими данными ОБЯЗАНЫ включать пункт «всегда
`PYTHONIOENCODING=utf-8` или `sys.stdout.reconfigure` в Python-скриптах, файлы —
`encoding='utf-8'`, JSON — `ensure_ascii=False`». Иначе субагент наступит на ту же грабли.

## Эхо консоли — НЕ доказательство состояния файла (2026-08-21, из петли самообучения)

stdout Git Bash на этой машине — cp1251. Кириллица, записанная в файл КОРРЕКТНО, при выводе
через `print()` в том же прогоне отображается как mojibake. Обратное тоже верно: «на экране
читается» не значит «в файле правильно».

**Правило:** судить о кириллице в файле только по повторному ЧТЕНИЮ файла — строгий
`decode("utf-8")` (без `errors="replace"`, чтобы порча падала, а не пряталась) плюс, при
сомнении, `unicodedata.name()` ожидаемой строки. Никогда — по эху консоли того прогона,
который писал.

Цена ошибки двусторонняя: можно «чинить» то, что не сломано, а можно принять mojibake за
норму. Класс — C-001 (наличие выхода принято за наличие результата), поверхность — вывод
инструмента вместо состояния объекта.
