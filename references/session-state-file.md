# §30 SESSION-STATE.md — снапшот сессии для восстановления после /clear

> **Примечание к публичной копии.** Файл выгружен из приватной рабочей конфигурации: имена контуров заменены ролями, личные пути — плейсхолдерами. Ссылки на файлы, отсутствующие в этом репозитории (реестры скиллов и инструментов, журналы инцидентов, история), указывают на приватные части конфигурации и намеренно не публикуются.

**Зафиксировано оператором 2026-07-11.**

## Проблема
`/clear` обнуляет контекст сессии — активные линии, договорённости, ключевые пути, следующий шаг. Проектный CLAUDE.md автозагружается новой сессией, но он статичен — в нём НЕТ «где мы сейчас». Ручная вставка snapshot первым сообщением работает, но требует действия оператора и уязвима к забыванию. Решение — сохранять снапшот в файл при явных триггерах.

## Механика
Каждый контур/агент оператора (§11) кладёт свой снапшот в **корень своей рабочей папки** под именем `SESSION-STATE.md`. Новая сессия при старте (после загрузки CLAUDE.md проекта) читает этот файл, если он существует и свежий, — подхватывает контекст без вставки от оператора.

### Путь по контуру
| Контур | Файл |
|---|---|
| надзорный | `<work-root>\надзорный\SESSION-STATE.md` |
| домашняя-автоматика | `<work-root>\домашняя-автоматика\SESSION-STATE.md` |
| радон | `<work-root>\радон\SESSION-STATE.md` |
| Чистые помещения | `<work-root>\CleanRooms\SESSION-STATE.md` |
| остальные | `<project-root>\SESSION-STATE.md` |

Файл лежит в приватной папке контура — на публичный git НЕ пушится (§20 приватность папок агентов, для надзорныйа — доп. §Д-5).

## Триггеры перезаписи
Перезаписывать снапшот при:
1. **Явной команде оператора:** «сохрани state / готовься к clear / snapshot / обнови session-state».
2. **Закрытии значимой линии:** публикация страницы, merge PR, milestone, релиз, закрытая задача из TaskList. После успеха — обновить, доложить «state обновлён».
3. **Пороге контекста ≥80%** (§6; пересчитано #CTX-1 2026-08-14 под 1M-окно): предложить обновление + `/compact` или `/clear`.

НЕ триггерить перезапись на каждый ход — это фиксация состояния, не audit-лог.

## Триггеры чтения
При старте новой сессии в проекте, после загрузки CLAUDE.md:
1. Если `SESSION-STATE.md` в корне проекта существует И его `last update` **≤7 дней** от текущей даты — Read его первым делом, до ответа оператору.
2. Если старше 7 дней — предупредить оператора («state устарел, дата X»), не действовать по устаревшему плану.
3. Если файла нет — старт с чистого листа по CLAUDE.md.

## Что писать в SESSION-STATE.md
- **Роль/контур** (одна строка).
- **Дата last update** (обязательно, в первой строке).
- **Активные линии** — что завершено недавно, что в работе, что backlog. Ссылаться commit-hash / URL / путь.
- **Ключевые пути** — где лежат исходники, локальные клоны, методички, история.
- **Дизайн-система / конвенции сессии** — если наработана (переиспользуемые CSS/шаблоны/паттерны).
- **Checklist текущих процедур** — секрет-скан, публикация, деплой.
- **Security invariants в силе** — приоритетные правила, чтобы новая сессия их не потеряла.
- **Триггеры собственной перезаписи** (мета-раздел, чтобы новая сессия знала когда обновлять).
- **Следующий шаг** — «ждать оператора» / «доделать X» / «проверить Y».

## Что НЕ писать
- Секреты, пароли, токены, ключи, PII оператора (даже в приватной папке — гигиена; если папка утечёт, снапшот с секретами хуже CLAUDE.md).
- Полный transcript диалога — снапшот, не журнал.
- Гипотезы «мы решили может быть …» без факта — только зафиксированные решения.
- Детали чужих зон (§12) — только свои.

## Формат
Markdown, 1 файл, `## Заголовки`, `**last update: YYYY-MM-DD**` в первой значимой строке (парсится глазами и Grep-ом). Компактный — ≤200 строк желательно; если больше — вынести историю в `SESSION-HISTORY.md` рядом.

## Anti-patterns
- Писать снапшот каждый ход — фиксация превращается в шум, оператор перестаёт доверять.
- Забыть обновить дату — новая сессия сочтёт файл устаревшим (или наоборот, актуальным при устаревшем содержании).
- Класть в публичный git — секрет-скан не защитит от полного дампа состояния.
- Дублировать CLAUDE.md — снапшот про «где мы», CLAUDE.md про «как работаем». Не путать.
- Слишком длинный снапшот — превращается во второй CLAUDE.md, ест контекст новой сессии. ≤200 строк.
- Полагаться только на снапшот при критичных решениях — оператор всегда может уточнить; снапшот — стартовый контекст, не источник истины.

## #CMP-1 — SESSION-STATE и автокомпакт (2026-08-26, надзорный)

**Статус находки — важно для честности.** Дефект конструктивный, найден чтением конфигурации и
хуков, а НЕ по следам инцидента: на 2026-08-26 автокомпакт ни разу не сработал сам (снапшот-хук
пишет поле `Триггер: manual/auto`; все компакты 24-26.08 — `manual`). Мера ставится до события.
Первичная формулировка правила ошибочно ссылалась на «инцидент этой сессии» — это была
экстраполяция: SESSION-STATE тогда устарел не от автокомпакта, а потому что был написан по
команде «готовь компакт» до завершения активной работы. Ошибка исправлена в тот же день; класс
её — #AH-1 (свойство конфигурации выдано за наблюдённый факт).

**Проблема.** Триггер §30 п.3 звучал «контекст ≥80% — ПРЕДЛОЖИТЬ обновление».
Между предложением и ответом оператора автокомпакт (`autoCompactEnabled: true` в
`settings.json`, порог ~967k) успевает сработать сам: он не спрашивает, не ждёт хода агента и
не привязан к согласию. Файл при этом остаётся старым.

**Почему существующая механика дыру не закрывала.** Три хука уже стояли и работали:
`context_guard.py` (предупреждение на 80/90%), `precompact_snapshot.py` (снапшот ДО сжатия),
`postcompact_restore.py` (требование прочитать SESSION-STATE ПОСЛЕ). Но снапшот сохраняет
**механику** (какие файлы правились, какие команды шли, последние реплики оператора), а не
**замысел** (зачем, какие решения приняты, что осталось незакрытым) — это прямо написано в
самом снапшоте: «содержит ТОЛЬКО механику … не замысел». Требование же обновить устаревший
файл стоит в `postcompact_restore.py` — то есть ПОСЛЕ сжатия, когда замысел уже потерян и
обновлять его нечем. Проверка стояла не на той стороне границы.

**Правило.** На пороге (§6, ≥80%) SESSION-STATE обновляется САМИМ агентом в том же ходе, без
запроса разрешения: это собственный control-space контура, не чужая зона и не необратимое
действие. Предложение `/compact`/`/clear` идёт ПОСЛЕ обновления, а не вместо него. Отказ
оператора от сжатия не отменяет обновления — файл уже актуален, ничего не потеряно.

**Что писать в состоянии перед сжатием — приоритет именно такой:**
1. Незакрытые хвосты и точка, где работа прервана (самое дорогое при потере: механику видно из
   снапшота, а «на чём остановились и почему» — нет).
2. Решения, принятые в этой сессии, и их причины (особенно правила, зафиксированные оператором
   дословно).
3. Расхождения/споры, ещё не разрешённые фактом.
4. Активные линии и следующий шаг.

**После автокомпакта — не достраивать по памяти.** Если восстановленный SESSION-STATE старше
последней значимой работы, честно сказать оператору «замысел за период X потерян, восстанавливаю
из снапшота и транскрипта», и проверять фактом каждое утверждение о состоянии диска. Память
после сжатия ненадёжна по построению — это не фигура речи, а свойство механизма.

**Остаточный риск (не закрыт текстом).** Между 80% и порогом автокомпакта агент может не
получить ни одного хода (длинный tool-call, фоновая задача) — тогда правило не успевает
сработать вообще. Механическая мера: `precompact_snapshot.py` должен САМ проверять возраст
SESSION-STATE и писать в снапшот явное «файл устарел на N часов» — тогда после сжатия видно, что
именно потеряно. Не реализовано на 2026-08-26 (правка кода хука — за оператором).
