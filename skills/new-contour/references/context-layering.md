# Context-layering strategy — снижение always-on контекста через дробление

Полное тело правила HL-6. Lean-императив + триггеры — в `SKILL.md` (раздел HL-6).
Этот reference — методика, шаблоны, anti-patterns, провенанс. Грузится on-demand.

История применения (рефакторинг 2026-06-16):
- `~/.claude/CLAUDE.md` 93 КБ → 27 КБ (−71%), архив в `~/.claude/doctrine-history-2026-06-15.md`.
- `Цензор/CLAUDE.md` 21 КБ → 12 КБ (−44%), архив в `audit/CLAUDE-Censor-history-2026-06-15.md`.
- Always-on memory floor упал с 114.8 КБ до 38.8 КБ (−66%).

После рефакторинга разведка показала, что та же логика просится на скиллы:
`spectravibe-dev/SKILL.md` (90 КБ, явное смешение слоёв), `esp32-dev/SKILL.md` (76 КБ),
`mikrotik-rb3011/SKILL.md` (26 КБ, инцидент-нарратив встроен в начало). Это правило
гарантирует, что НОВЫЕ контуры и скиллы не повторяют эту ошибку с первого дня.

---

## 1. Load-frequency ladder (модель платы за контекст)

Каждый артефакт знания агента сидит на одном из 4-х уровней. Цель — держать содержимое
на самом нижнем уровне, где оно ещё доступно.

| Уровень | Что грузится | Когда платится | Бюджет |
|---|---|---|---|
| **L1 — Always-on** | `~/.claude/CLAUDE.md` + `<project>/CLAUDE.md` | **каждая** сессия **каждого** агента | **HARD ≤ 14 КБ суммарно** (8 глобал + 6 проект) |
| **L2 — Trigger-on** | `SKILL.md` тело + frontmatter description | когда description-триггер матчится | **HARD ≤ 8 КБ на ядро SKILL.md** |
| **L3 — On-demand** | `references/*.md`, `scripts/*`, `templates/*` | ТОЛЬКО при явном `Read` агентом | не лимитировано |
| **L4 — Never-auto** | `audit/`, `<skill>-history-*.md`, `CHANGELOG.md`, `incidents/`, `_drafts/` | только по специальному запросу оператора / диагностике | не лимитировано |

Ключевая идея: **/compact и /clear НЕ снижают L1**. Memory-файлы перегружаются
идентично. Единственный способ срезать always-on пол — отредактировать файл и
вынести содержимое на L3/L4.

## 2. Правило 3-слойного разреза (центральный приём)

Любой документ-знание агента (CLAUDE.md / SKILL.md / PROJECTS.md / TaskList.md / реестр)
делится на 3 слоя:

| Слой | Что это | Куда |
|---|---|---|
| **A — Императив** | «делай так / никогда не делай Х» в одном предложении | inline в L1/L2 |
| **B — Методика** | «почему именно так», шаблоны, код-примеры, развёрнутые процедуры | `references/<topic>.md` (L3) |
| **C — История** | «инцидент 2026-XX-XX → побудило правило», прецеденты, narrative | `<file>-history-<date>.md` или `audit/` (L4) |

В lean-файле остаётся только A + одна строка-указатель: «детали — B, история — C».

### Маркеры, по которым выносить (любой = триггер):
- Дата в формате `2026-MM-DD` или `INC-NN` в теле → это **C** (история), уноси.
- Цитата оператора verbatim длиннее 1 строки → **C**.
- Code-блок ≥ 15 строк → **B** (методика/шаблон).
- Таблица анти-паттернов «✗ ... ✓ ...» с обоснованием каждой строки → **B**.
- Narrative «эта система так устроена потому что…» длиннее 5 строк → **B**.

### Что НИКОГДА не выносить из L1/L2:
- **Реестры** (агенты, скиллы, папки, ключи, $names массивы) — это contiguous lookup-list, режется только целиком.
- **Safety-locks / privacy-locks** («НИКОГДА не push», «ПРИВАТНЫЙ control-space», «X DISABLED») — риск пропустить слишком высок.
- **Имена файлов и абсолютные пути**, на которые ссылаются другие правила — рвутся ссылки.
- Императив сам — это А, он inline по определению.

## 3. Файловая раскладка по типам контента

| Контент | Файл-куда | Уровень |
|---|---|---|
| Императив «никогда X / всегда Y» | inline в SKILL.md/CLAUDE.md | L1/L2 |
| Реестр (агенты/скиллы/папки/MAC-адреса/имена сервисов) | inline | L1/L2 |
| Safety-lock / privacy-lock / freeze-marker | inline | L1/L2 |
| Index-таблица «правило → reference → archive» | inline (начало файла) | L1/L2 |
| Методика «как делать X» длиннее 20 строк | `references/how-<topic>.md` | L3 |
| Шаблон кода / конфига / промпта | `references/template-<name>.md` | L3 |
| Таблица anti-patterns с обоснованиями | `references/antipatterns-<topic>.md` | L3 |
| Инцидент с датой («2026-XX-XX случилось X») | `INCIDENTS.md` или `<skill>-history-<date>.md` | L4 |
| Changelog скилла (SemVer-bumps) | `CHANGELOG.md` | L4 |
| Длинная narrative «почему эта система такая» | `references/background-<topic>.md` | L3 |
| Список known-issues / зомби-багов | `KNOWN-ISSUES.md` | L4 |
| Drafts / proposals / черновики | `audit/_drafts/` или `<project>/_drafts/` | L4 |
| Freeze-снимок состояния проекта | `audit/freezes/freeze-<date>.md` | L4 |
| Бинарные дампы, RAG-индексы, бэкапы | `<project>/_backups/` или `_indexes/` | L4 (не грузится никогда) |

## 4. Триггеры рефакторинга существующего файла

Если **любое** из ↓ — пора резать:

1. SKILL.md > 8 КБ.
2. Проектный CLAUDE.md > 6 КБ.
3. Глобальный CLAUDE.md > 8 КБ.
4. В одном файле одновременно: (а) императивные правила + (б) narrative обоснования > 5 строк + (в) хотя бы одна дата инцидента / цитата оператора. Это **смешение слоёв** — самый сильный сигнал.
5. Файл вырос ≥ 30% за последний месяц активной работы — растёт history-шум.

## 5. Lossless-протокол рефакторинга (HARD-обязателен)

Срезать НИКОГДА не значит «удалить». Алгоритм каждого рефакторинга:

```
1. Verbatim backup (mandatory FIRST):
   cp <file> <file>-history-<YYYY-MM-DD>.md   # архив, никогда не auto-load
2. Прочитать архив целиком (не lean-версию).
3. Маркером пройти каждую секцию: A / B / C ?
4. Создать references/<topic>.md для каждого B-блока.
5. Если C-блок отдельный (история конкретного правила) — оставить в backup
   и сослаться на конкретный раздел; если C-блоки разбросаны — собрать в
   <file>-history-<date>.md (это и есть backup, оно покрывает обе роли).
6. Переписать исходный файл lean: только A + index-таблица указателей.
7. Sanity: grep по lean-файлу всех safety-локов из исходника — должны найтись verbatim.
   Реестры — тоже verbatim grep всех строк таблиц.
```

**Backup — это lossless-гарантия.** Без него рефакторинг запрещён. Backup никогда
не auto-load (он не в L1/L2), оператор/Цензор зовут его явно при разборе инцидента.

### Index-таблица в lean-файле (обязательная шапка)

```markdown
## ИНДЕКС — где полное тело и где история

| Правило | Полное тело (reference) | История (архив) |
|---|---|---|
| <rule-1> | references/<topic-1>.md | <file>-history-<date>.md §<section> |
| <rule-2> | references/<topic-2>.md | <file>-history-<date>.md §<section> |
```

Это превращает lean-файл в навигационную карту, а не в «огрызок без контекста».

## 6. Применение к новым контурам (bootstrap-обязанность)

При onboarding нового контура через `new-contour` Phase 0 + Phase 4 (см. SKILL.md):

**Phase 0 (confirm intent) — добавить вопрос оператору:**
- «Ожидается ли у этого контура CLAUDE.md проекта или регламентные документы > 6 КБ?»
- Если да — Phase 4 сразу проектирует папочную структуру `references/` + `audit/`.

**Phase 4 (NEW — context-layering setup):**
1. Создать в проекте контура каркас:
   - `<project>/CLAUDE.md` (lean, ≤ 6 КБ, только A)
   - `<project>/references/` (для B)
   - `<project>/audit/` (для C: history, инциденты, failure-register)
   - `<project>/scripts/` (для helper-кода, см. правило #15-16 глобального CLAUDE.md)
2. Если контур получает первый IMPORTANT-инцидент или operator-мандат с датой —
   ОДНОВРЕМЕННО с записью императива в CLAUDE.md создать запись в
   `audit/incidents-<YYYY-MM>.md`. Не «потом отрефакторим».
3. SKILL.md контура (если он его делает — например, custom workflow-скилл) — с самого
   начала писать по 3-слойному правилу: ядро ≤ 8 КБ, длинные методики в references/.

**Самый частый и опасный анти-паттерн новых контуров:** «временно положу инцидент в
CLAUDE.md, потом вынесу». Через полгода CLAUDE.md = 90 КБ. Дисциплина: дата в теле
правила = повод СРАЗУ создать `incidents-<month>.md`, а в CLAUDE.md оставить только
указатель «(детали — `audit/incidents-2026-06.md` §INC-07)».

## 7. Carve-outs (когда правило неприменимо)

- **Малый файл, не растёт.** Если SKILL.md < 5 КБ и за месяц не вырос — оставить как
  есть, преждевременная оптимизация хуже бойлерплейта references.
- **Один человеческий читатель.** Внутренний реестр оператора (`PROJECTS.md` для
  собственного навигационного удобства, не загружаемый агентами) — оптимизировать не
  обязательно. Только если он мешает контексту реально загружающих его агентов.
- **Бинарные дампы / RAG-индексы.** RasPi5 Backup/ (38 МБ), Секретарь corpus-индексы
  (35 МБ) — это L4 по факту (никто не Read их целиком). Не трогать.
- **Реестры и safety-locks.** См. §2 «что НИКОГДА не выносить». Перевес L1-бюджета
  именно за счёт этих блоков — это нормально и приемлемо.
- **Явное слово оператора.** «Не дроби этот файл» — приоритет над правилом.

## 8. Anti-patterns (наблюдённые)

✗ **Смешение слоёв в SKILL.md** (`spectravibe-dev` 90 КБ, `esp32-dev` 76 КБ): правила
+ операторские мандаты-с-датами + инциденты в одном теле. Каждый триггер скилла
грузит весь архив.
✗ **«CHANGELOG.md рядом, но в SKILL.md дублируется narrative»** — половина-меры. Если
есть CHANGELOG, в SKILL.md инцидентов быть не должно вовсе, только указатель.
✗ **Удаление вместо вынесения** — теряется lossless-гарантия, провенанс правила
исчезает, через год никто не помнит почему была мандата.
✗ **Срезать lean-файл ниже бюджета за счёт safety-локов** — выгода 2 КБ, риск
потерять privacy-lock необратимый.
✗ **Index-таблица без abs-путей** — «см. references/X» вместо
`references/X.md §3` — Reader-агенту приходится искать секцию вручную.
✗ **Backup-файл в always-on пути** — `<file>-history-<date>.md` ВНУТРИ папки скилла
рискует попасть под триггер, если description слишком жадный. Архив CLAUDE.md
держать рядом с CLAUDE.md (он не auto-load), архив SKILL.md — рядом с SKILL.md
ИЛИ в `audit/` проекта.

## 9. Brief для subagent при делегировании рефакторинга

Если рефакторинг делегируется фоновому субагенту — бриф ОБЯЗАН включить:

1. **Lossless-инвариант**: «verbatim backup ПЕРВЫМ шагом до любой правки исходника».
2. **Список safety-локов** (verbatim-фразы, которые должны остаться в lean-файле дословно).
3. **Список реестров** (которые нельзя выносить).
4. **Бюджеты по уровням** (L1 ≤ 14 КБ суммарно, L2 ≤ 8 КБ на ядро).
5. **Anti-hallucination**: сверка результата через `grep` по lean-файлу всех safety-фраз
   и всех строк реестров — должны найтись verbatim. Если хоть одна не найдена — FAIL.
6. **Что вернуть**: финальные размеры (было/стало), путь к backup, список созданных
   references, список безуспешно-выносимых блоков с обоснованием.

Шаблон брифа — в этом же скилле, `references/refactor-brief-template.md` (создавать
по мере накопления опыта).

## 10. Метрики успеха

Считать рефакторинг успешным, если **все** выполнены:

- L1 (CLAUDE.md global + project) ≤ 14 КБ.
- L2 (SKILL.md всех скиллов агента) ≤ 8 КБ каждое ядро (carve-out: реестры/safety-локи).
- Все safety-locks и реестры verbatim найдены в lean-файле через `grep`.
- Backup-файл byte-identical с исходником (cmp / sha256).
- Index-таблица в шапке lean-файла указывает на КАЖДЫЙ вынесенный блок.
- Ни один императив не потерян (subagent-бриф проверяет по списку).

Допустимый перерасход бюджета L1/L2 — только за счёт неразрезаемых блоков
(реестры, safety-локи). Декларировать перерасход и обосновать в финальном отчёте.
