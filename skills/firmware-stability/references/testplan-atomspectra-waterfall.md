# Пример приёмочного тест-плана: atomspectra-waterfall-esp32 + wf-recorder

**Происхождение:** первый полный прогон лестницы фаз этого скилла (0-8) на реальной паре
проектов — прошивка водопада ESP32 + ПК-приёмник. Составлен и исполнялся контуром
Codeaudit, 2026-08-20, по мандатам оператора #ST-1…#ST-5 (два стенда А/Б, один испытатель,
DOC-N не правится испытателем, часть сценариев отложена). Сохранён по правилу §17
(«тест-планы под стандартные запросы — готовы заранее в SKILL.md/references») и по
прямому указанию оператора «все скрипты сохраняй и добавляй вместе с текущим планом в
скилл проверки».

**Как использовать как шаблон:** структура (мандаты → объекты испытаний → роли → стенды →
9 ступеней → матрица сценариев с приоритетами P0-P3 → встроенный самоаудит → критерии
готовности → границы → предусловия) переносима на любую пару «встроенное устройство +
ПК-клиент». Специфика этого проекта (ASWF-формат, конкретные API-эндпоинты, конкретные
номера issue) — не переносить буквально, метод — переносить.

**Живой журнал исполнения** (числа, находки по мере прогона, не статичен) — НЕ здесь, а в
приватной папке контура-исполнителя: `Codeaudit\reports_local\supertest-foundation\LOG.md`
(gitignored — может содержать факты о живом стенде оператора, в скилл не копируется).
Инструмент для CRC-проверки `.aswf`-файлов, извлечённый по ходу этого прогона, —
`scripts/aswf/verify_aswf.py` рядом с этим файлом.

## 2. Роли

| Роль | Кто | Что делает |
|---|---|---|
| Испытатель комплекса | **Codeaudit** | все ступени, оба конца (плата по WiFi + ПК-инструменты), журнал прогонов, дефект-репорты |
| Физические действия | **Оператор** | питание, OTG, перенос платы, окно для деструктивных шагов; каждый шаг по чек-листу «действие → ожидаемое наблюдение» |
| Чинящая сторона (прошивка) | **ESP32** | фиксы по дефект-репортам file:line; правки доков (DOC-N, #ST-4) |
| Чинящая сторона (приёмник) | **Программист** | фиксы wf-recorder по дефект-репортам |
| Стерильная проверка | субагенты/скрипты без моего контекста | пересчёт чисел от первички, слепые проходы перед вердиктом (§31.A) |
| Приёмка вердикта | Оператор (по моему заключению с двумя стерильными проходами) | решение «фундамент готов / не готов» |

**actor≠verifier:** я не автор ни одной строки испытываемого кода. Конфликт «испытатель =
аудитор» гасится стерильными проходами: вердикт не уходит без двух слепых проверок моих чисел.

## 3. Стенды (#ST-2)

| | Стенд А — диагностический | Стенд Б — продуктовый |
|---|---|---|
| Плата↔ПК | UART-кабель подключён, консоль `idf.py monitor` | нет кабеля |
| Питание | от UART-кабеля ПК | стационарный БП 5V (уточнение оператора 20.08: повербанка не будет) |
| Данные | всё равно по WiFi (продуктовый путь не меняется) | только WiFi |
| Назначение | ступени 4–5, диагностика невоспроизводимого | ступени 3, 6, 7, 8; все полевые сценарии |
| Зачёт приёмки | **НЕТ** | **ДА** |

Правило перехода: дефект со стенда Б воспроизводим на А ради следов; зачёт — только Б.
Следствие для Б: следы обязаны жить на плате (причина ребута, `seg_lost`/`seg_evicted`,
debug-лог S-19, кольцо мониторинга 12 ч) — их живучесть проверяет ступень 3 ДО нагрузки.

## 4. Лестница ступеней

Порядок по цене ошибки (скилл `firmware-stability`): дешёвое и воспроизводимое — раньше;
наблюдаемость — до нагрузки, без исключений.

### Ступень 0 — Фиксация и предусловия (хост, ~полчаса)
- SHA обоих репо, `version.txt`, версия прошивки на живой плате (страница «Система»").
- Чек предусловий: плата прошита **1.2.17**, спектрометр подключён OTG, WiFi доступен,
  Python-окружение для wfr на ПК, стационарный БП 5V для стенда Б.
- Если версия платы ≠ HEAD репо — стоп, прошивает оператор/ESP32, не я.
- **Выход:** таблица версий в журнале прогона; расхождений нет.

**Факт 20.08 при старте:** репозиторий ушёл вперёд прямо во время написания плана —
`8b01ddf`/1.2.17 (был `f92f710`/1.2.16). Оператор подтвердил тестировать 1.2.17
(включает #FW-63, прямо по S-43). Клон в scratchpad обновлён fast-forward. Что физически
стоит на плате — проверяется первым делом этой ступенью, не предполагается.

### Ступень 1 — Готовые тесты обеих сторон + мутационная приёмка (хост, без железа)
- fw: `tests/host` — 7 модулей (`test_roundtrip`, `test_shproto`, `test_kv_array`,
  `test_flash_quiet`, `test_hist_stage`, `test_net_time`, `test_debug_log_filter`), Makefile.
- wfr: все 12 `test_data*.py` + `test_timeout_survival.py`.
- **Мутационная выборка #SA-3** (тест обязан уметь краснеть): по 3 теста с каждой стороны
  нарочно ломаю проверяемую функцию в рабочей копии → тест обязан упасть → откат мутации.
  Выбор мутантов: по одному на класс (целостность, протокол, состояние).
- **Выход:** все зелёные; каждый выбранный мутант пойман. Тест, не поймавший мутанта, —
  находка P2 владельцу («зелёный тест на неисправленном коде значит, что тест не тот»).

### Ступень 2 — Контракт протокола на фикстурах (хост, без железа)
- Против `PROTOCOL.md` + `ASWF_FORMAT.md`: разбор listing, сегментов v4/v5, CRC, ack.
- Жёсткие кейсы S-48: чужая схема заголовка, sizemismatch, битый CRC (двухпроходное
  удержание), огрызок хвоста; S-44 (переиспользование имён после перенумерации);
  S-45 (старый state без отпечатков); S-49 (смена v4→v5, ротация шва, перенос калибровки).
- Фикстуры: реальные сегменты с платы (снятые на ступени 5) + синтетика с внесённой порчей.
- **Выход:** ни один кейс не приводит к тихой порче файла шва; каждая порча наблюдаема
  (эскалация/лог/удержание ack) — сверка с докой, расхождения → DOC-N.

### Ступень 3 — Наблюдаемость на продуктовом стенде Б (гейт перед нагрузкой)
Три вопроса скилла письменно, до любого длительного прогона:
1. Зависание → что останется? (web-UI жив/мёртв, TCP-мост, кольцо мониторинга)
2. Ребут → сохранится ли след? (причина ребута на «Системе», debug-лог S-19, счётчики
   `seg_lost`/`seg_evicted` в status S-55 — читаются ли ПОСЛЕ ребута по WiFi)
3. Деградация → какие счётчики её покажут? (heap на «Системе», кольцо 12 ч #MON-2/`9e0f409`,
   USB-диагностика `/api/usb-diag`: `cdc_error_count`, `rx_watchdog_trips`, `reconnect_ok`,
   `last_fault_reason` — появились с фиксом #FW-51, KNOWN_ISSUES.md:245-246)
- Проверка фактом: контролируемый ребут (оператор), затем чтение всех следов по WiFi.
- **Выход:** все три ответа «да» с доказательством. Любое «нет» — стоп, дефект-репорт
  владельцу, нагрузка не начинается.

### Ступень 4 — Базовые метрики (стенд А)
- Покой и типовая запись (интервал 60 с): heap/PSRAM, стеки задач, RSSI, CPS-поток —
  снимками во времени (board_snapshot + страница «Система» + консоль).
- **Выход:** базовая линия в журнале. Без неё «стало хуже» на soak не с чем сравнивать.

### Ступень 5 — Функциональные пользовательские сценарии (стенд А; P0-повторы на Б)
Матрица 56 сценариев (раздел 5). Порядок: сначала цепочка первого пользователя
(S-01→S-02→S-04→S-05→S-08), затем P1, затем P2. Каждый сценарий: действие → наблюдаемый
критерий → артефакт (скриншот/файл/JSON status) в журнал.
- Сверка «док ↔ поведение» на каждом шаге (#ST-4): расхождение → DOC-N, не стоп.
- **Выход:** P0/P1 зелёные (или дефект-репорт + повтор после фикса, ≤2 круга — W-005);
  P2 допускают задокументированные отклонения.

### Ступень 6 — Хаос и сбои (стенд Б; физика — оператор)
По одному внесённому отказу за раз (#DBG-1: одна переменная):
- обрыв WiFi при заборе (S-42) — выключение AP/роутера (плата на стационарном БП —
  «унос из зоны» моделируется пропаданием сети, не переносом платы);
- снятие питания платы на живой записи (S-43) — оператор; после подачи: `spectrogram_restore`,
  новый сегмент, потеря видна в `seg_lost`, баланс сходится;
- выдёргивание OTG при водопаде (S-50) — пауза строк, `dur=interval+1` соседней строке;
- перенумерация сегментов после ребута (S-44) — клиент опознаёт по отпечатку, не удаляет;
- заполнение flash долгой записью без забора (S-46) — кольцо keep-last, `flash_full=true`,
  `seg_evicted` растёт, забор учащается → запись продолжается;
- kill приёмника посреди прохода (S-42/`test_c3_delete_interrupt`) — рестарт без потерь/дублей;
- ~~полевой цикл целиком (S-36)~~ — **ОТЛОЖЕН оператором 20.08 (#ST-5)** вместе с S-33
  (fallback-Outdoor): в текущий супертест не входят, из зачёта приёмки исключены.
  Ручное включение Outdoor тумблером (S-32) остаётся в ступени 6 как smoke — это
  штатная кнопка, не требующая пропадания домашней сети.
- **Выход:** после каждого отказа — восстановление без вмешательства в данные; сквозной
  баланс строк сходится (инструменты ступени 7 гоняются после каждого кейса).

### Ступень 7 — Сквозная целостность двумя независимыми путями
- Путь 1 (штатный): `board_snapshot.py --light` до/после + `balance_check.py
  --before --after --seam` — «ни одна строка не потеряна».
- Путь 2 (независимый свидетель): мой отдельный скрипт-пересчёт строк/CRC файла шва
  напрямую по `ASWF_FORMAT.md` — НЕ переиспользующий код wfr (иначе общий дефект невидим).
  Пишется по спеке через Ollama (§31.B), приёмка запуском + мутацией. **Реализован** —
  `scripts/aswf/verify_aswf.py` рядом с этим файлом (переиспользуемый, не только для этого
  прогона).
- Сверка сумм: строки платы (status) = строки шва = строки независимого пересчёта;
  температурные точки `temps.csv` согласованы с числом строк.
- **Выход:** три числа сходятся на записях ступеней 5–6 и на soak ступени 8.

### Ступень 8 — Soak и приёмка (стенд Б)
- Непрерывная запись ≥24 ч (превышает эталоны 9.4 ч #STAB-2 и 11 ч rec12) с периодическим

## 6. Самоаудит (встроенный, §31.A + #SA-3)

1. **Журнал прогона** — единственный источник чисел: каждый шаг — артефакт (файл, JSON,
   скриншот, лог) в `reports_local\supertest-foundation\<ступень>\`. Число без артефакта
   в отчёт не попадает.
2. **Мутационная приёмка** тестов и моих же инструментов (ступень 1 и скрипт ступени 7):
   «работает» принимается только вместе с «ломается, когда должно».
3. **Стерильные проходы:** после ступени 2 (полнота кейсов порчи), после ступени 8 (два
   слепых прохода перед вердиктом). Брифы — задача/метод/критерий, без моих чисел.
4. **Гейт W-007** механически не выпустит заключение без отметки стерильной проверки.
5. **Дефект найден мной → чинит владелец → проверяю по коду и повтором сценария**, не по
   письму автора (приём 13); ≤2 круга на линию (W-005).
6. **Разметка достоверности** [Ф]/[В]/[Г]/[П] во всех документах супертеста.

## 7. Критерии «фундамент готов к развитию»

1. Все P0-сценарии зелёные на стенде Б (не А).
2. P1 зелёные либо отклонения задокументированы и приняты оператором явно.
3. Soak ≥24 ч: 0 незапланированных ребутов; баланс строк сходится тремя путями; heap-дрейф
   в пределах базовой линии ступени 4.
4. Мутационная проверка: тестовые наборы обеих сторон умеют краснеть.
5. Открытые баги перечислены с оценкой влияния; ни одного открытого P0.
6. DOC-находки переданы ESP32 (#ST-4); критичные для пользователя — исправлены.
7. Два стерильных прохода подтвердили отчёт; расхождения разобраны до вердикта.

Невыполненный пункт — в отчёт как есть, без округления в свою пользу; решение о снижении
планки — только оператор.

## 8. Оценка длительности (календарно, с фоновыми прогонами)

| Ступени | Оценка |
|---|---|
| 0–2 (хост) | 1 день |
| 3–4 (стенды, метрики) | 0.5–1 день, нужно окно оператора (ребут-проверка следов) |
| 5 (56 сценариев) | 1–2 дня |
| 6 (хаос) | 1 день, окна оператора на физику |
| 7–8 (целостность + soak + приёмка) | 24–48 ч фонового soak + 1 день приёмки |
| **Итого** | **~5–7 дней** при доступности железа и окон оператора |

## 9. Чего супертест НЕ делает (границы)

- Не правит код и доки испытываемых проектов (находки — владельцам; DOC-N — ESP32, #ST-4).
- Не аудирует физику спектрометрии (корректность спектров прибора — вне рамок; проверяется
  транспорт и целостность, не наука).
- Не тестирует offload на внешний HTTP-сервер дальше локальной заглушки (S-31 — smoke).
- Не выполняет деструктивных действий без оператора (раздел 0).
- **Не шлёт прибору команды настройки, меняющие заводскую конфигурацию** (`-U`/`-V`/`-ris`,
  обработка импульсов, температурная компенсация, режекция): открытый BUG-AS-08 —
  «шлюз не резервирует заводскую DSP-настройку прибора» (KNOWN_ISSUES.md:77), отката нет.
  S-09 ограничивается безопасными информационными командами (`-inf` и т.п.); S-18
  (бэкап/восстановление регистров) выполняется ТОЛЬКО при явном согласии оператора и
  после успешного «Скачать бэкап».
- Не включает flash encryption и не меняет секретов платы (необратимо — INSTALL.md:233).
- Не гарантирует отсутствие отказов — только их наблюдаемость и перечисленное покрытие
  («отсутствие отказа за сутки ≠ его отсутствие» — длительность и условия пишутся в отчёт).

## 10. Предусловия от оператора для старта

1. Плата с v1.2.16, спектрометр на OTG, стационарный БП 5V — в наличии и рабочие.
2. Окна на физику: ребут-проверка (ступень 3), хаос-кейсы (ступень 6), старт soak (ступень 8).
3. Подтверждение снятия стопа на управляющие команды плате (раздел 0) — зафиксировано 20.08.
4. «Старт» на исполнение этого плана.

## Урок процесса, зафиксированный этим прогоном (переносимый на любой похожий супертест)

- **Реальная плата почти всегда даёт факты, которые план не предвидел** — на ступени 0
  живой `/api/system` сразу показал реальную версию, на ступени 3 первый же контролируемый
  ребут (побочный, при переключении стенда) дал БЕСПЛАТНОЕ реальное доказательство сценария
  «ребут посреди записи» — не нужно было имитировать искусственно.
  «Составитель списка путей не может сам гарантировать его полноту» — тест-план и
  стерильный проход должны сходиться на реальном железе, а не только на бумаге.
- **Гейт наблюдаемости (ступень 3) — не формальность.** На этом прогоне он реально нашёл
  два дефекта (отсутствие `esp_reset_reason()`, отсутствие coredump-раздела) ДО начала
  нагрузки — именно то, для чего он существует.
- **API может отвечать `{"ok":true}`, ничего не сделав** — поймано вживую при попытке
  сменить `interval_sec` (неверный ключ, надо было `interval`). Универсальный урок:
  ЛЮБОЙ config-эндпоинт проверять не по коду ответа, а по факту изменения состояния
  (`GET .../status` после `POST` с заведомо неверным телом).
- **Мутационная приёмка ловит и собственные процессные ошибки испытателя**, не только
  дефекты кода: `python file.py` вместо `python -m pytest file.py` дал 11 false-green
  прогонов подряд (см. W-008 в журнале инцидентов Codeaudit) — поймано до доклада именно
  привычкой не доверять «exit=0» без осмысленного вывода.
